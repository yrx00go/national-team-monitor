能做。但**「国家队买入比例」这个说法必须改掉** —— ETF 份额变化是事实，**「谁买的」永远是推断**。

## 二、为什么不用他的「倍量」算法

他定义「1 倍量 = 2025 年末峰值份额的 0.1%」，然后拿这个**固定分母**衡量 2026 年每天的变化。

实测 510050 全年份额：

```
2026-01-05   565.9 亿份
2026-02-02   251.8 亿份
2026-06-01    84.5 亿份
2026-10-09    71.2 亿份
2026-11-05   161.9 亿份
```

**分母定死在年末，分子一年变了 8 倍**，算出来的百分比越来越没有意义。
而且 2026 年 1 月这波 −89%，如果分母用年末份额，指标会被直接拉到负无穷。

### 本站的「水位」指标

```
水位(t) = 份额(t) ÷ median(份额[t−20 … t−1]) − 1
百分位  = 水位(t) 在过去最多 250 个水位值中的分位
```

三个设计理由：
1. **滚动基准** → 不受份额折算、规模漂移影响
2. **中位数不用均值** → 抗单日异常申购
3. **输出百分位不只输出百分比** → 回答「现在算高还是低」，不是「今天变了多少」

### 归一化 → 双轴零点对齐（用户第二轮反馈后改的）

第一版合并用的是**归一化**：份额、价格都除以各自起点换算成「指数（起点=100）」，共用一根左轴。
零点唯一、读数唯一，逻辑上最干净。

但用户看截图后直接说：`纵坐标房价格`（应该是「放价格」）——**他要的是左轴直接显示价格（元），
不要「指数 100」这种二次加工的量。这是对的：一张讲价格的图，纵轴就该是价格。**

于是改成：**左轴＝价格（元），右轴＝份额（亿份）**。这里有个必须守住的点 ——
7.13 那次「读数骗人」的根子不是「有两根轴」，而是**两根轴各自自动缩放、零点落在不同高度**（差 32.8pp），
同一像素能读出两个都对数。所以这次不是简单回到双轴，而是**把两根轴的零点强制对齐**：

```js
y : {position:'left',  beginAtZero:true, ...}   // 价格
y1:{position:'right', beginAtZero:true, ...}   // 份额
```

**实测：两轴 0 线高度差 = 0.00px**，左轴 `0~4.00 元`、右轴 `0~700 亿份`，两轴最低刻度都是 0。
零点对齐后，左轴读价格、右轴读份额，各读各的，不会互相冒充。

**代价要说清**：`beginAtZero` 压低了数据利用率 —— 价格 2.10~3.76 元放在 0~4 的轴上，只占 **42%** 高度
（自动缩放能到 93%）。份额占 85%。
**这是一个显式的权衡：牺牲一点图形饱满度，换「读数不会错」。** 反过来选更容易出错。

**判据：双轴不是绝对不能画。真正的禁忌是「两根轴零点不同高」。**
只要两边 `beginAtZero`，零点对齐，双轴就是安全的；否则必须拆图。

**过程中否掉了自己的一个方案**（值得记）：本来还想把「累计净流入」也画进这张叠加图，
实测它与份额的**相关系数 0.982** —— 因为份额变化就是累计净流入对时间的积分，
两条线本质是同一条的两种刻度，画出来必然贴着走。强行画两条会让人误以为有两个独立信号，
那是**新的误导**。所以只留「数量（份额）」和「价格」这两条真正互补的线，
累计净流入降级到 tooltip 里悬停显示。
**判据：叠加两条线之前，先算它们的相关系数。高于 0.95 就不该画两条。**

### 组合页：净申赎上下分图 → 单张「点位 × 资金」（2026-11-11 晚，用户第三轮反馈）

用户原话：`也改为一张图；且增加上证指数的走势；纵坐标为上证指数的点位`。

**演进三步，每一步的原因都不同，别混：**

| 版本 | 形态 | 为什么改 |
|---|---|---|
| ① | 单张双轴（柱左轴＋线右轴） | 两轴各自自动缩放，零点差 32.8pp → 读数骗人（见 7.13） |
| ② | 上下分图（上柱下线上） | 回避双轴，读数安全，但「钱 vs 位置」的对照关系也没了 |
| ③ | **单张双轴（左=点位，右=金额）** | 用户要一张图 + 要上证点位做主纵轴 |

**③ 的关键：两根轴的缩放策略故意不同，这不是偏心。**

```js
y : {position:'left',  /* 不设 beginAtZero */}   // 上证点位
y1:{position:'right', beginAtZero:true}          // 累计净流入
```

- **右轴（金额）必须 `beginAtZero`**：零是「不进不出」，是这张图唯一的语义分界线（线上=净买入，线下=净卖出）。
- **左轴（点位）不能 `beginAtZero`**：3200 点里没有「零」这层含义，从 0 起算是无信息的留白。
  实测若强制从 0 起算，1582 点的跨度只占 **35.2%** 绘图高度（128px/365px），指数被压成一条直线。

**这与单只页的处理相反，原因在量的性质不同，不是判据变了。**
单只页价格 2.09~3.76 元、0 有意义（跌到 0 就是归零），所以两边都 `beginAtZero`；
这里点位 2660~4243、0 无意义，所以只有金额轴对齐零。

**代价（必须写在页面上）**：两轴零点不再重合（点位轴压根没有零刻度）。
消歧方式从「对齐零点」换成「**每根线标注读哪一侧**」——legend、轴标题、轴刻度颜色三处都写。

**为什么可以叠（先算相关系数，不是凭感觉）**：
`corr(上证指数, 区间累计净流入) = −0.1258` —— 近乎无关，是两个独立信号。
对比单只页 `corr(份额, 累计净流入) = 0.9821`，那条才必须降级到 tooltip。

**单日净流入柱为什么没画**：1660 个交易日在 ~1150px 宽里，每根柱不到 1px，远看是一条灰带，
还会盖住指数线。它的信息（当日+区间+规模+成员数）全部挪进 tooltip。

### 数据区间：为什么是 2020-01-02

用户要求「能查到的最早数据」，实际验证结果：

- 上交所份额公示接口实测**可回溯到 2017 年甚至更早**（2017-01-03 返回 78 只、目标 3 只命中；2020-01-02 返回 169 只）

### 6.1 「换成 GitLab 行不行」—— 查证结论：不行

| 平台 | runner 位置 | Pages | 免费额度 | 结论 |
|---|---|---|---|---|
| **GitHub.com** | 境外 | ✅ 无限（公开仓库） | Actions 无限 | **问题和 GitLab 一样** |
| **GitLab.com** | **美国**（官方文档：Linux x86-64 在 `us-east1` / `us-east5`，ARM64 在 `us-central1`，全部跑在 Google Cloud） | ✅ | **400 计算分钟/月** | ❌ 换汤不换药 |
| **极狐 GitLab（gitlab.cn）** | 国内 SaaS，但**未公开 runner 地域** | ✅ 支持 | 基础版，额度需登录看 | ⚠ 可能行，但三件事要先确认 |
| **Gitee Pages** | 国内 | **已下线**（官方 2024 年公告） | — | ❌ 不可用 |

**核心判断：换 CI 平台解决不了「出口在境外」这件事。** GitLab.com 的 runner 在美国，和 GitHub 是同一个问题。

极狐 GitLab 是唯一可能真解的方向，但必须先确认：
① 免费版是否开放 SaaS 共享 runner、给多少分钟；② 免费版 Pages 是否支持自定义域名 + 自动部署；
③ **最要紧：它的 SaaS runner 部署在国内哪里、能否直连上交所/深交所**（官网无公开说明）。

**真正推荐的两条路**：
1. **先跑一次 GitHub 的 `workflow_dispatch`**。能通就不用折腾（日频数据，偶尔重跑完全够）。
2. **如果 runner 被拦，加一个「国内出口」**：抓取那步改由国内小机器/云函数触发，GitHub 只负责构建发布；
   或直接用对象存储静态托管（腾讯云 COS / 阿里云 OSS）+ 国内定时任务，成本约每月几块钱。

#### 6.1.1 ⚠ 上面这个结论的因果说重了（2026-11-11 晚修正）

上面整张表的前提是「runner 在境外 → 一定抓不到」。**实测之后这个前提站不住，必须修正：**

| 测试 | 结果 |
|---|---|
| 本机出口归属 | **香港**（`101.32.221.79`，腾讯云），**不是中国大陆 IP**；且开着代理 `HTTP_PROXY=127.0.0.1:58281` |
| 香港 → 上交所，带 `Referer: https://www.sse.com.cn/` | **200，0.29 s，103 564 字节，923 只全部返回，目标 7/7 命中** |
| 香港 → 上交所，`Referer` 换成 `example.com` | **`success:false`** |
| 香港 → 上交所，不带任何头 | **`success:false`** |
| 香港 → 上交所，只带 Referer 不带 UA | **正常** → 关键头就是 Referer，UA 不要紧 |
| 香港 → 深交所 XLSX 快照 | **200，0.22 s，36 KB** |
| DNS 解析 | `query.sse.com.cn → 202.122.113.77`（上海）、`www.szse.cn → 58.251.50.138`（深圳），**无按地域调度到海外的迹象** |

**修正后的判断：**
- 交易所接口的门槛**主要在请求头（Referer 必须是本站域名），不在 IP 归属**。「境外一律不通」这句话是错的，香港能通就是反例。
- 但**不能反过来说「GitHub 一定行」**。香港可以 ≠ 美国弗吉尼亚可以，中间还隔着出口策略和长链路。
  社区里确实有不少 GitHub Actions 项目记录「美国服务器访问国内财经数据源失败」，但那些多是东财/新浪这类有反爬的接口，
  **不等于交易所官方接口一定失败**。
- **诚实结论：风险比我原先写的小，但没有被消除。** 唯一能确定的方式仍然是真跑一次 `workflow_dispatch`。
  在跑之前，不该拿间接证据拍板。

#### 6.1.2 ✅ 已真跑：这个环节闭环了（2026-11-12，GitHub Actions `ubuntu-latest`，美国弗吉尼亚）

**结论：交易所官方接口在境外 runner 上能通；东财会被随机掐断。两者必须分开说。**

| 数据源 | 结果 | 明细 |
|---|---|---|
| **上交所** ETF 份额 | ✅ **能抓** | `2026-11-11 ✅ 7 只`（11-09/10 已有跳过，11-12 尚未发布）|
| **深交所** XLSX 快照 | ✅ **能抓** | 5 只，写入 `2026-11-11`，自建历史累积 3 天 |
| **两融余额**（交易所口径） | ✅ **能抓** | 3500 天，`2012-06-14 → 2026-11-11`，余额 23,023 亿，占流通市值 2.49% |
| **东财 `push2his`**（价格 / 上证指数） | ❌ **不稳定** | 同一次运行里 3/10 成功、7/10 `RemoteDisconnected`；下一次 0/10 |

**所以最后那一句「不该拿间接证据拍板」是对的，但拍板之后得到的答案比预期好：**

- 「境外 IP 一律抓不到」**被证伪**。上交所/深交所在美国弗吉尼亚正常返回，门槛确实是 `Referer` 而不是 IP。
- 但「东财一定抓得到」**也不成立**。东财 `push2his` 对境外 IP + 高频连打做了间歇性掐断，
  典型瞬时错误 —— 同一台 runner 上交易所全通、只有它挂。重试 4 次（0.8/2/4 s 退避）能救回一部分，救不回全部。
- **这个组合恰好是可接受的**：核心口径（份额、两融）来自交易所，稳定；
  价格只用于「净流入 × 当日价」，缺几只时用旧价顶上，误差落在该标的当日涨跌幅里，比整块归零好得多。

**唯一仍然未闭环的是 GitLab.com runner**（地域不同，理论上同样能通，但没有实测，不写「一定行」）。

### 6.2 为提高境外 runner 成功率做的三处加固

| # | 问题 | 改法 |
|---|---|---|
| 1 | 上交所接口**不带 `Referer` 返回 `success:false`，但 HTTP 状态码仍是 200** | 加显式判断 `js.get('success')=='false'`，避免「被拒绝」被当成「当天没数据」 |
| 2 | 两个交易所接口原来是 **HTTP** | 全改 **HTTPS**（实测正常，SSE 返回 103 KB 完整数据） |
| 3 | `update.py` 把价格/重算/股息率标成「失败也继续、不报警」 | 改为记录失败 + 末尾非零退出码；workflow 区分「降级发布」与「核心失败」 |

第 1 条是最隐蔽的：接口用 200 返回拒绝，而代码把「当天无数据」当成非交易日放行 —— **真实失败被「非交易日不报警」的机制掩盖了**。

### 6.4 GitLab 定时任务的三处硬差异（配置全文见 `.gitlab-ci.yml`）

| # | GitHub | GitLab | 踩坑表现 |
|---|---|---|---|
| 1 | cron 写在 workflow 文件里 | **必须网页建**：项目 → Build → Pipeline schedules | 文件里写 `cron:` 不会报错，但**永远不触发** |
| 2 | 产物路径任意 | **必须叫 `public/`**，job 名**必须叫 `pages`** | 名字或路径错了 → 站点 404，且无明确报错 |
| 3 | 公开仓库 Pages 默认开 | **免费版需手动启用**：Settings → General → Visibility → Pages | job 显示成功，但站点打不开 |
| 4 | `GITHUB_TOKEN` 默认能 push | **`CI_JOB_TOKEN` 默认不能 push**，要手动开 | `git push` 得到 403，报错**完全没提**是权限开关 |

**还有一条最容易忽略的**：GitLab CI 的 `rules` 没有匹配项时，job 被**静默跳过** —— 不报错、不提示。
排查「为什么没跑」时先看 rules，不要先怀疑代码。

`.gitlab-ci.yml` 的 `rules` 设了四个入口：定时任务（`RUN_UPDATE=1`）、手动 Run pipeline、
schedule 兜底、`main` 分支 push。建 schedule 时把变量 `RUN_UPDATE` 设为 `"1"`。

**时区（已定案：用 `gitlab.com`）**：GitLab schedule 的 cron 用**实例时区**，GitLab.com 是 UTC。
所以「22:10 北京时间」写成 **`10 14 * * *`**，和 GitHub Actions 的写法完全一样。
（若将来改极狐 `jihulab.com` 且实例时区是 CST，则要改成 `10 22 * * *` —— 这一处最容易错一小时。）

#### 6.4.1 第 4 条要展开说：`CI_JOB_TOKEN` 为什么推不了代码

这是本文件里唯一一处「照着 GitHub 的习惯写、但 GitLab 直接不给过」的地方，值得单列。

GitLab 官方文档原话：**「您可以配置您的项目，以允许使用 CI/CD 作业令牌进行身份认证的
Git 推送请求。此设置默认关闭。」** 默认状态下 `CI_JOB_TOKEN` 只能 `clone`/`pull`
（以及读写 Registry、下载 artifacts），**唯独不能 push**。这是刻意的最小权限设计，
防止被注入的构建脚本偷偷改源代码。

**对本项目来说，这一条不是「锦上添花」，是「数据会不会有洞」：**

| 数据 | 抓取方式 | 不 push 回仓库的后果 |
|---|---|---|
| 沪市 ETF 份额 | 上交所支持任意历史日期查询，可随时全量回补 | 无所谓，明天再抓一次就补上 |
| **深市 ETF 份额** | **接口忽略日期参数，永远只返回「当前」快照** | **那一天的份额永久缺失，补不回来** |
| 两融 / 成交额 | 接口支持历史 | 无所谓 |

也就是说，**推送这一步决定了深市那 6 只（159919 / 159922 / 159845 / 159915 / 159545）
的自建历史是连续的还是断的**。断一天就是永久断一天。

两条路，二选一（`.gitlab-ci.yml` 对两者都支持，优先用 `PUSH_TOKEN`）：

| | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | Settings → Access Tokens 建一个 Developer + `write_repository` 的令牌 → 存为 CI/CD 变量 `PUSH_TOKEN`（勾 Masked） | 一个令牌要维护，但不动仓库权限模型 |
| **B（最省事）** | Settings → CI/CD → Expand「Job token permissions」→ 勾「Allow Git push requests to the repository」 | 一个勾选框，但等于给所有 job 开了推送权 |

两种情况都要注意：如果 `main` 是**只允许 Maintainer 推送**的保护分支，CI bot 仍会被拦。

**兜底设计（这次顺手补的）**：`.gitlab-ci.yml` 里

- 推送失败时**不甩 403**，而是打一段 ✗ 提示，写清该去哪个菜单勾什么；
- `update` job 标了 `allow_failure: true`、artifacts 标了 `when: always` ——
  否则「数据抓到了、只是没推回去」会让依赖它的 `pages` 被**直接跳过**，
  页面反而发不出去。现在退化成「页面更新了、但仓库历史有洞」，至少当天数据能看。

⚠ **但这个兜底有代价，必须知道**：`allow_failure: true` 意味着**抓取真的失败时，流水线也不报红**，
只显示橙色感叹号。GitLab 不像 GitHub 那样有内置的失败邮件提醒（要自己建 Webhook / 通知集成）。
所以**它不会主动喊你**，只能靠你自己回头看。两个补法，按成本：

| 做法 | 效果 |
|---|---|
| 每周手动看一眼项目首页的流水线状态 | 够用，成本最低 |
| Settings → Integrations 配一个 Webhook（钉钉/企微机器人）监听 `pipeline` 事件 | 失败能推消息，但要多配一个东西 |

在配通知之前，**别把「页面还在更新」当成「抓取没出问题」** —— 页面用的是上一次的数据。

### 6.5 两融发布的时点差（新增）

| 数据 | 可得时间 | 说明 |
|---|---|---|
| 两市成交额 | **T 日当晚** | 收盘即定 |
| ETF 份额 | **T+1 早间** | 交易所 T 日晚发布 |
| 两融余额 | **T+1 晚间** | 交易所次一交易日公布 |

所以一次定时任务里，三份数据的最新日期本来就可能差一天。这**不是 bug**，
面板上分别标注各自日期（见 11.4 的对齐陷阱）。

### 方案二：小程序（自己用，不给别人）

**但「自己用」绕开了这一层** —— 看版本对照：

| 版本 | 谁能访问 | 需审核 | 需备案 | 需类目资质 |
|---|---|---|---|---|
| 开发版（预览） | 只有开发者 | ❌ | ❌ | ❌ |
| **体验版** | **后台加的体验成员（最多 15 人）** | **❌** | **❌** | **❌** |
| 正式版 | 所有微信用户 | ✅ | ✅ | ✅ |

**体验版常驻、不过期**（过期的是单张二维码，重新生成即可）。

#### 但还有第二道硬限制：个人主体不能用 `web-view`

> 微信官方文档原文（`web-view` 组件）：「会自动铺满整个小程序页面，**个人类型的小程序暂不支持使用**。」

后果很具体：**个人主体后台根本没有「业务域名」配置入口**，`web-view` 写了会在真机直接报错。

**这条把「把现有 HTML 塞进小程序」这条路直接判死。** 而且本页面的数据是 `build_demo.py`
内联进 HTML 的 1.7 MB 单文件，`web-view` 载入本地 HTML 本来也不成立（需要 HTTPS 托管域名）。

#### 那还剩三条路，按代价排序

| # | 做法 | 工作量 | 体验 | 结论 |
|---|---|---|---|---|
| **A** | **不注册小程序，把页面存成手机书签 / 加到主屏** | **0** | 已实测可用（见下） | ✅ **推荐** |
| B | 企业主体 + `web-view` 内嵌现有页面 | 注册企业主体 + 域名 + 备案 + HTTPS + 业务域名校验 | 最接近现状 | 只为一个自用页面办营业执照，不划算 |
| C | 原生小程序重写（WXML/WXSS + 图表按 canvas 重画） | **7 张图全部重写**，约等于把整个前端再做一遍 | 最原生 | 除非你想要「下拉就能看」的入口，否则不值 |

#### 为什么推荐 A：我实测过现有页面在手机上就能用

用 iframe 强制 390px 视口（headless Chrome 最小窗口 500px，直接测会失真）：

**结论：不需要小程序也能在手机上正常看。** 具体做法二选一：

- **iPhone**：Safari 打开 → 分享 → **添加到主屏幕** → 桌面出现图标，全屏无地址栏，跟 App 一样

配合方案一，页面在 GitLab Pages 上有个固定网址，加一次主屏就行，以后每天点开看当日数据。

#### ⚠ 修正：使用设备是小米 Android，上面那条 Android 写法不成立

原方案给的是「iPhone Safari → 添加到主屏幕」。**这条在 Android 上不成立**，
在小米设备上更不成立 —— 因此重新查证了一遍 Android 的安装路径。

**① 小米浏览器对 PWA 的支持是 0/4 —— 四项行为一个都没有**

| 浏览器 | PWA 支持 | 「添加到桌面」 | 装成独立 App（无地址栏） |
|---|---|---|---|
| **小米浏览器** | **❌ 全无** | ✅（路径绕） | ❌ |
| Chrome for Android | ✅ | ✅ | ✅（生成 WebAPK） |

2018 年 MIUI 9 Global Beta 的更新日志曾宣布支持 PWA，但**那篇论坛帖已下线，现在没有任何现行文档支持**。
所以小米浏览器**永远不会弹「安装应用」** —— 它只会建一个普通桌面快捷方式。

**② MIUI 有三个隐藏开关会静默拦住快捷方式**

```
① 「创建桌面快捷方式」权限在 MIUI 14+ 默认关闭，且首次使用【不弹窗申请】
   路径：设置 → 应用设置 → 应用管理 → 小米浏览器 → 权限管理 → 启用「创建桌面快捷方式」
   ⚠ 不是「安装未知应用」、不是「读取桌面布局」，名字很像但都不是
② 第三方 Launcher（Nova / Action）会绕过 MIUI 的 ShortcutManager 集成，忽略 PWA 元数据
   → 切回 MIUI 默认桌面
③ MIUI「极简模式」会禁用所有动态快捷方式 API 调用栈
   → 关掉极简模式再试
```

**③ 所以给了两条路，按「要不要折腾」分**

**路 A：0 改动，现在就能用（小米浏览器）**

```

```

- 「添加快捷方式」会问你加到**浏览器首页**还是**手机桌面** —— 选错就白做，只在浏览器里多个书签

**路 B：装 Chrome，装成真 App（无地址栏、进「设置→应用」、可卸载）**

需要页面这边补 PWA 元件 —— **原来一条都没有，所以这条路之前根本走不通**：

| 元件 | 原来 | 现在 |
|---|---|---|
| `manifest.json` | ❌ 无 | ✅ 新建（name/short_name/start_url/display:standalone/theme_color/background_color/prefer_related_applications:false） |
| `<link rel="manifest">` | ❌ 无 | ✅ 已加到 head |
| 图标 192×192 | ❌ 无 | ✅ `icons/icon-192.png` |
| 图标 512×512 | ❌ 无 | ✅ `icons/icon-512.png` |

| `theme-color` | ❌ 无 | ✅ `#1C1917` |
| `background_color` | ❌ 无 | ✅ `#FAFAF9`（缺这个会白屏闪一下） |
| 页面内安装按钮 | ❌ 无 | ✅ 自己画的，见下 |

**为什么必须自己画按钮**：Chrome 的自动提示受 **engagement heuristic** 约束 ——
用户得在页面上交互过一小段时间才弹。第一次打开、看一眼就退出，**一辈子不会弹**。
自己画的按钮不受这个延迟限制：一收到 `beforeinstallprompt` 就存下来，点按钮即装。

**三种状态必须分开处理，否则会变成点不动的假按钮**：

| 状态 | 判据 | 显示 |
|---|---|---|
| 已装 | `display-mode: standalone` 或 `navigator.standalone` | 整条不显示 |
| 可装 | 收到 `beforeinstallprompt` | 真按钮，点了弹系统框 |
| 不支持（小米/微信/其它） | 1.5 秒内没收到事件 | 换成「你这个浏览器该点哪里」的一句话 |

页面上实际长这样（390px，小米 UA 实测）：

```

       点 ⋮ → 工具箱 → 添加快捷方式 → 选「手机桌面」        [✕]
```

**只在手机上显示**：桌面浏览器打开时整条不显示 —— 桌面用户本来就没有「桌面」可加，是纯噪声。
判据用 `pointer: coarse` + 宽度，**不只看宽度**（iPad 横屏 1024px 也该显示，桌面窗口拖窄到 400px 不该显示）。

**④ 踩过的三个坑（都实际发生过）**

```

   —— 实测改了之后 54 / 71，视觉平衡

   → 打开先空 900ms，然后整块内容猛地下移，比闪一下难受得多
   → 改成一开始就 paint 中性文案，盒子立刻占位、高度固定，后续只换文字不产生位移

   → 砍成一行，54px。手机上这条最多占 56px（一行标题 + 一行说明）
```

**⑤ ★ 最要命的连带影响：Pages 只发 index.html + data/，manifest 和 icons 会被漏掉**

`GitLab Pages` 那一步原来是：

**manifest.json 和 icons/ 不在里面 → 线上 404 → Chrome 静默失败**：
不报错、不提示，就是永远不出现安装按钮。这是排查这类问题最费时的一种 ——
本地双击打开能通（相对路径都在），线上一装就不行。

已修，两个 CI 文件都补了 `cp manifest.json` + `cp -r icons`，并加了 `test -f` 自检。
**这条也写进了「数据自查清单」之外的一份 PWA 自查清单**（见下）。

**⑥ 本地实测（`python3 -m http.server`，所有资源逐个 curl）**

> **manifest 必须是独立文件、必须和页面同源可达、必须走 http/https。**

**⑧ 顺带修掉的一个老问题：390px 下 4 张 KPI 排成 3+1**

|---|---|---|---|---|
| 原 auto-fit(118px) | **3+1** | 139px | 122px | 252px |
| 改成 2 列 | 2×2 | **212px** | **105px** | **218px** |

**卡更宽、更矮、整块还短了 34px** —— 不是妥协，是纯改进。
360 / 430 / 500 / 640 / 900 / 1440 六个宽度全部回归，无横向溢出、无卡内文字溢出。

> （`cdnjs.cloudflare.com/.../chart.umd.js`，205 KB）。手机上如果 CDN 被墙，图会全空、文字还在。
> 若要走「完全离线」，`build_demo.py` 里把 Chart.js 也内联进去即可（文件从 1.7 MB → 1.9 MB）。

**这条已经做成开关了**（2026-11-12）：

```bash

python3 scripts/build_demo.py --offline  # 离线版   1.85 MB（Chart.js 内联）
```

Chart.js 首次运行会下载一次并缓存到 `scripts/vendor/chart.umd.js`，之后不再联网。
**替换用的是完整标签匹配**（`<script src="...">` 整段换掉），不是正则改 `src` 属性 ——
属性顺序或写法一改，正则就会静默漏掉，而整段匹配找不到会直接报错。

| 版本 | `typeof Chart` | 图表数 | 结果 |
|---|---|---|---|
| CDN 版 | `false` | **0** | 文字全在、**图全空** |
| 离线版 | `true` | **7** | 全部正常 |

**这就是那个缺口的真实样子**：不是「加载慢」，是**图一张都没有**。

### 方案三：定时任务在 GitLab 怎么跑

**核心一句：GitLab 的定时任务不在 `.gitlab-ci.yml` 里配，必须在网页上建。**
文件里写 `cron:` 不会报错，但**永远不触发** —— 这是从 GitHub 迁过来最容易踩的一条。

#### 完整步骤（照做即可）

**① 网页建 schedule**

```
项目 → Build → Pipeline schedules → New schedule
  Description   每日更新
  Interval Pattern  10 14 * * *        ← UTC 14:10 = 北京 22:10
  Cron timezone     [UTC]              ← 保持 UTC，别改
  Target branch     main
  Variables         RUN_UPDATE = 1     ← 关键，否则 rules 可能不匹配
```

**② 时区换算**（已定案用 `gitlab.com`，实例时区是 UTC）

| 想要的北京时间 | 填的 cron |
|---|---|
| **22:10**（主，收盘后 4 小时） | **`10 14 * * *`** |
| 08:10（兜底，补前一天） | `10 0 * * *` |

⚠ **和 GitHub Actions 写法完全一样**（两边都是 UTC）。若将来换极狐 `jihulab.com` 且实例时区是 CST，
要改成 `10 22 * * *` —— **这一处最容易错一小时，且错了不会报错，只是时间不对。**

**③ 四个入口都在 `rules` 里**（`.gitlab-ci.yml` 已写好）

```yaml
rules:
  - if: '$RUN_UPDATE == "1"'                    # 定时任务
  - if: '$CI_PIPELINE_SOURCE == "web"'          # 手动 Run pipeline
  - if: '$CI_PIPELINE_SOURCE == "schedule"'     # 兜底：schedule 没设变量也跑
  - if: '$CI_COMMIT_BRANCH == "main" && $CI_PIPELINE_SOURCE == "push"'
```

⚠ **`rules` 没有匹配项时，job 被静默跳过** —— 不报错、不提示，流水线看起来「成功但什么都没做」。
**排查「为什么没跑」先看 rules，不要先怀疑代码。**

**④ 三处和 GitHub 的硬差异**（详细踩坑见 6.4）

| # | 差异 | 踩坑表现 |
|---|---|---|
| 1 | cron 必须网页建 | 写文件里永不触发 |
| 2 | 产物必须 `public/`、job 名必须 `pages` | 404，无明确报错 |
| 3 | `CI_JOB_TOKEN` 默认不能 push | 403，报错完全不提是权限开关 |

**⑤ 它不会主动喊你**

`update` job 标了 `allow_failure: true`（为了「推送失败也别挡住发页面」），代价是

## 七、技术错误修正记录（累计 53 处，全部已修）

### 7.1 净流入不能用前复权价（2026-11-11 早上修）

`净流入 = 份额差 × 当日真实成交价`。前复权会把历史价系统性压低：

| 标的 | 前复权 | 不复权 | 偏差（2024-06-03） |
|---|---|---|---|
| 上证50 | 2.367 | 2.502 | −5.40% |
| 沪深300 | 3.376 | 3.587 | −5.88% |
| 红利 | 2.957 | 3.242 | −8.79% |
| 中证红利 | 1.397 | 1.567 | −10.85% |

导致 2024 年那段的净流入被低估 3%~11%，越往前偏得越多。全区间累计差额 **90.6 亿元**。

**现在的规则：画价格曲线用前复权（趋势连续、无分红断层），算净流入用不复权（当日真实价）。两套价格，两个用途。**

### 7.2 机构存活率的基准期选错了（2026-11-11 早上修）

第一版拿「最新一期报告」当基准，结果 7 只全部 >100%（因为最新一期本身就在份额已经砍掉之后的低点）。

**修正：基准改用「机构持股最高的那一期」。** 那才是「国家队曾经拿了多少」。

### 7.3 组合规模也用了前复权价（2026-11-11 复查时发现）

同一类错误，**7.1 修了净流入，规模这里漏了**。

| 口径 | 2023-12-01 | 2026-11-10 | 涨幅 |
|---|---|---|---|
| 前复权（错） | 3,278.4 | 5,310.9 | **+62.0%** |
| 不复权（对） | 3,466.9 | 5,310.9 | **+53.2%** |

**凭空多长出 8.8 个百分点的涨幅。** 而且因为最新一天复权基准无偏差（2026-10-27 起两者相等），
只看最新值或只看首尾两天，肉眼完全看不出破绽 —— 这类错误的隐蔽性就在这里。

### 7.4 四象限百分比合计会出现 99 / 101（2026-11-11 复查时发现）

页面上写着「四格加起来 100%」，实际 3 只标的是 99 或 101（各自 round 的必然结果）。
**改用最大余数法分配**，7 只现在全部严格等于 100。

### 7.5 存活率「峰值期 = 最新一期」时没有标注（2026-11-11 复查时发现）

中证红利的峰值期恰好是 2026-06-30（即最新一期）。此时 275.9% = 最新一期 ÷ 它自己所在最高点，
**只反映「份额一路涨」，没有任何证明力**。原来和「未触及该证明」混在一起显示，会被读成「机构还在大力买」。

**改法**：新增 `peak_is_latest` 字段，表里单独标注「此证明退化为份额扩张，无信息量」。

### 7.6 股息率配对：我改错了一次，已完全回退（2026-11-11 复查）

我曾判断「中期配上一财年年度」是「跨财年混搭」（因为把 2025 上半年 + 2024 全年加在一起看着像一年半），
改成「严格同一财年」。结果与本地另一套独立缓存对不上：

| | 我的新算法 | 原有口径 | 本地缓存实际 |
|---|---|---|---|
| 工商银行 | 0.3103 → 3.60% | 0.3200 → **3.73%** | 3.73% ✅ |

回去读那套已经跑通多年的 `dividend_notify.py` 才明白**原有口径才是对的**：它算的是「按当前派息节奏，往前推一个完整年度能拿到多少」。
对银行这种「中期 + 年度」稳定派息结构，这才是正确的年化；按「同一财年」算反而拿到的是已经过去的 2025 全年。

**已完全回退，并把这次错误写进代码注释。** 现在 11 只与她缓存最大偏差 **0.08pp**，工行 3.73% 精确一致。

### 7.7 规模在涨、累计净流入是负的 —— 不是 bug，但页面没解释（2026-11-11 晚，用户要求复查时发现）

这是我这两轮里**最该早点看到**的一条：我一直在修「规模用错价」这个算术错误，
却没意识到把两个数字摆在同一页面上，任何人第一眼都会认为算错了。

| 指标 | 值 |
|---|---|
| 组合规模 2023-12-01 → 2026-11-10 | 3 466.9 → 5 310.9 亿（**+53.2%**） |
| 同期累计净流入 | **−979.7 亿** |

两者方向相反。拆开看就通了：

| | 份额（亿份） | 金额（亿元） | 均价（元） |
|---|---|---|---|
| 买入侧 | +7 024.3 | +19 088.4 | 2.717 |
| 卖出侧 | −6 713.4 | −20 068.1 | 2.989 |
| 净额 | +311.0 | **−979.7** | 卖出贵 **10.0%** |

**高换手 + 低买高卖**，份额净增而资金净流出，数学上完全成立。
「净流入」度量的是**买卖差额**，「规模」度量的是**期末存量**，两者本来就不是一回事。

**必须做的验证（否则这个解释是假的）**：组合层面的 10% 价差，可能只是「买 A 卖 B」的品种结构转移造出来的。
所以必须**逐只**算 —— 实测 **6/7 只**卖出均价高于买入均价，说明是**每只内部**的低买高卖，不是品种搬运；
唯一例外是科创50（−3.1%），它是真割肉，必须单独显示出来，不能被组合数字平均掉。

已在「监控组合」页新增拆解面板（`calc_turnover` / `calc_turnover_combo`）。

### 7.8 把「会变的数」写死在静态 HTML 里（2026-11-11 晚，自己写完就发现）

7.7 的拆解面板，我第一版把 `规模 +53%`、`累计净流入 −980 亿` **硬编码进 HTML 标题**。
这个站是日更的，明天数据一变，标题就成了假话 —— 而且是那种「看起来还很权威」的假话。

**已改为全部由数据实时计算**，包括标题文本本身。

> **规则：凡是「会随数据变化的数」，一个都不能出现在静态 HTML 里。**
> 判断方法很简单 —— 这个数明天还会是它吗？不会，就必须走 JS。

### 7.9 「区间累计」在水下：我解释了「为什么矛盾」，但没解释「为什么是负的」（2026-11-11，用户看着图问出来的）

用户贴了监控组合那张图的截图问：**「区间累计还是在水下，是什么含义？为什么区间累计还会是负的？」**

我一开始以为 7.7 已经答过了。**没有。7.7 回答的是「为什么 −980 和 +53% 不矛盾」，
用户问的是「这条线为什么会跑到零以下」。这是两个问题。**

而且我当时连这条线的基本事实都没说清：

| | 值 |
|---|---|
| 起点 2023-12-01 | 0.0（定义上归零） |
| 峰值 2024-10-11 | **+4 423.4 亿** |
| 谷值 2026-07-01 | **−4 389.4 亿** |
| 期末 2026-11-10 | **−979.9 亿** |

**它中途到过 +4 423，不是一路净流出。** 这句话不说，「区间累计为负」就会被读成「国家队这三年一直在跑」。

**根本答案是恒等式，不是形容词。** 光说「两者口径不同」是废话，必须给出可验算的分解：

```
规模(t) − 规模(t−1) = (份额(t)−份额(t−1)) × 价格(t)      ← 净流入（申赎）
                    + 份额(t−1) × (价格(t)−价格(t−1))    ← 存量浮盈
```

实测：规模变化 **+1 844.0** = 净流入 **−979.8** + 存量浮盈 **+2 823.8**，**残差 −0.0，可精确重算**。

> 一句话：**钱是被「卖出去」的，规模是被「涨出来」的。**
> 这两件事在数学上完全独立，方向相反毫无问题。

穿零轴的是哪一段也算了：2026 上半年撤退单段 **−7 298.6 亿**，把曲线从 +2 936.9 砸到 −4 361.7；
7–10 月回补 **+3 381.8 亿**，只拉回 −979.9。**补得很猛，但没把上半年撤出去的全买回来。**

**新增 `calc_bridge()` / `calc_cum_path()`**，页面加「这条蓝线为什么在水下」面板，就在图的正下方 ——
用户是在那张图上产生疑问的，解释必须放在同一屏。

**两个自我校验已内置**：
- `bridge.resid` 不为 0 时，面板会自己报红「本段解释不成立，需要先查口径」，而不是继续输出一段漂亮话；
- 净流入与浮盈必须用**同一套不复权价**。用前复权算浮盈会虚增，恒等式立刻破 —— 这正是 7.3 那个错误的同一个根，第三次碰到它。

**另外补了一个更稳的口径**：距峰值 **−5 403 亿**。
它比「−980 亿」更能说明钱去哪了，因为**它不依赖「从哪天开始算」** —— 而 cum 的水平完全由区间起点决定。
凡是区间累计类的指标，都该同时给一个不依赖起点的版本。

### 7.10 「含分红涨幅」算错：515080 被虚高 48.6pp（2026-11-11，用户问「三只红利走势为什么差这么多」）

用户问：`510880 + 515080 和低波红利的关系是什么，为什么份额差距如此大，但走势差距也很大。`

为了回答「走势差距」，我先算「含分红总回报」。**第一版用前复权价首尾相除，得出 515080 +145.1%。
这个数是错的，真实值 +96.5%，虚高 48.6pp。**

**错在哪**：我默认「前复权 = 分红再投资」，所以首尾相除就该是总回报。但我没验证一件事 ——
东财的 `fqt=1` 到底是**乘法复权**还是**减法复权**。实测结果是减法：

```
515080  2020-01-02  bfq=1.0740  qfq=0.6390  bfq−qfq=0.4350
        2020-11-27  bfq=1.3620  qfq=0.9270  bfq−qfq=0.4350   ← 恒定！
        2020-11-30  除息，差从 0.4350 掉到 0.3750（= 派了 0.06 元/份）
```

`bfq − qfq` 在除息前后恒定，说明复权方式是 `qfq(t) = bfq(t) − Σ_{t'>t} div(t')`。
**减法复权把历史价减掉一个常量，分母被系统性做小了，相除就把涨幅放大了。**
分红越密集、区间越长，放大越严重：

| 标的 | 前复权首尾相除（错） | TRI（对） | 虚高 |
|---|---|---|---|
| 510880 | +68.4% | +58.7% | +9.7pp |
| 515080 | +145.1% | **+96.5%** | **+48.6pp** |
| 159545 | +53.6% | +46.8% | +6.7pp |

**515080 从「涨了 1.5 倍」变成「涨了不到 1 倍」** —— 用户问的正是「差距大不大」，这个错误直接把答案歪掉了。

**第二条错路（也记下来，避免换过去）**：天天基金的「累计净值」。它的定义是
`LJJZ = DWJZ + 累计已分红`，即**单利**，不滚入再投资。实测 515080 的 `LJJZ − DWJZ` 从 0 走到 0.4350，
正好等于累计分红总额，确认是单利。用它算会**低估**：510880 单利 +38.2% vs 复利 +58.7%，差 20pp。

**正确做法只有一条 —— 逐日把分红按当天价格买回去（TRI）**：

```
TRI(t) = Π (bfq(t) + div(t)) / bfq(t−1)
```

**真正的救命一步是交叉验证**，不是推导。我用「净值 vs 它跟踪的指数」做了第二条独立路径：

| | 515080 | 000922 中证红利指数 |
|---|---|---|
| 2020-01-02 → 2026-11 | 单位净值 1.0759 → 1.5626，**+45.2%** | 4503.09 → 5540.86，**+23.0%** |

ETF 净值 +45.2%、指数只有 +23.0%，差值 22pp 正是分红（指数是纯价格，净值含分红现金流）。
**而「前复权相除 +145%」跟这两条路径都对不上，矛盾立刻暴露。**
如果我只跑一遍、不做这个对照，这个错会一直挂在页面上。

**顺带一个副产品**：这次反推分红用的是 `S(t) = bfq(t) − qfq(t)`，末日的 S 必然为 0，可自检。
算出来的 510880 累计 0.925 元/份（7 次，每年 1 月除息）、515080 累计 0.435 元/份（18 次，2024 起按季），
与之前独立查到的公告数据完全吻合。

> **规则：凡是「涨幅 / 收益率 / 年化」这类结论性数字，必须用第二条独立路径再算一遍。**
> 本轮的第二条路径是「净值 vs 指数」；上一轮的（7.1/7.3）是「不复权 vs 前复权」。
> 推导写得再漂亮也不算验证 —— **只有两条互相独立的路径对上了，才算。**

**⚠ 反推分红有一个明确失效边界**：`S = bfq − qfq` 只对**没做过份额折算**的标的成立。
份额折算（拆分/合并）会改变每份对应净资产，复权因子跟着跳，但那是折算不是分红。
实测 512100 反推出来单笔「分红」高达 **12.69%**、累计 **8.2 元/份** —— 全是
2022-08-03 拆分（1:1.46301）和 2022-09-02 合并（1:0.36555）留下的假事件。
**代码里已硬性禁止对 `SPLITS` 出现过的代码做这个反推。**

### 7.11 区间前推后，文案里的方向词全部反了（2026-11-11）

把起点从 2023-12 前推到 2020-01，累计净流入从 **−979.7 亿** 变成 **+1459.3 亿**（符号翻转）。
但页面上有 4 处文案是围绕「净流出」写的，全部变成假话：

| 位置 | 原文 | 问题 |
|---|---|---|
| `cumTitle` | 「这条蓝线**为什么在水下**：期末 …」 | 期末已是 +1460 亿，说「在水下」自相矛盾 |
| `cumBox` 正文 | 「所以它**可以**是负的…**中途穿越过零点**」 | 方向假设错了 |
| `turnTitle` | 「规模 +X%，累计净流入**却是** …」 | 「却是」预设了反向 |
| `turnBox` KPI | 副标题「看起来是**净流出**」 | 数字是 +1459.7，正数 |

**改法不是换几个字，而是按数据的正负分支**：`const netOut = T.net_amt < 0;` 然后两套文案。
这样明天数据翻回去，页面自动跟着变 —— 而不是又错一次。

这是第 4 次犯 7.8 那个错（把会变的东西写死在 HTML 里）。**判据还是那一句：
这个说法明天还成立吗？不成立就必须进 JS 分支。**

顺带发现一个更值得说的点：**净流入为正反而是个陷阱**。
规模涨 287%、净流入 +1460 亿 —— 看着像「大举买入」，实际净流入只解释了新增规模的
**约 38%**，剩下的 2410.8 亿全是存量浮盈。
所以页面现在会主动补一句「差额全部来自存量浮盈，不是新钱」。
**方向对了不等于含义对了。**

### 7.12 用「今天的数」去否定「用户在图上看的东西」（2026-11-11）

用户在旧区间（2023-12 起）的图上看到 510880 与 515080 差距很大，问「为什么份额差距如此大」。
我拿 2026-11-10 当下的数据回答：**「这三只现在的份额本身并不悬殊」** ——
这等于说他的观察是错的。**可他看的是对的，只是时点不同。**

按 2023-12-01 那一列：510880 53.7 亿份 / 161 亿，515080 25.9 亿份 / 37 亿 —— **规模差 4.4 倍**，确实很大。

真正该做的是给时间轴，而不是纠他一个数：

| 时点 | 510880 规模 | 515080 规模 | 规模差 |
|---|---|---|---|
| 2020-01-02 | 31 亿 | 2 亿 | **14.9 倍** |
| 2021-12-31 | 178 亿 | 9 亿 | **19.1 倍** |
| 2023-12-01 | 161 亿 | 37 亿 | **4.4 倍** |
| 2024-12-31 | 234 亿 | 66 亿 | 3.5 倍 |
| 2026-11-10 | 200 亿 | 111 亿 | **1.8 倍** |

**同一个问题在五个时点上答案差 10 倍以上，其中 2021 年末的 19 倍比 2020 年初还极端**
（那两年 510880 从 10.7 亿份暴涨到 61.7 亿份，515080 只从 2 亿走到 6.4 亿）。
所以「为什么份额差距这么大」这个问题，**得先问「在哪一天」**。

叠加第二层：份额差 ≠ 规模差。510880 单位净值是 515080 的两倍多，
所以 2023-12 的「份额差 2.1 倍」在金额上是「规模差 4.4 倍」。

> **规则：用户说「差距大」「不对」「奇怪」时，先确认他看的是哪个时点、哪张图，再判断对不对。**
> 拿最新一天的数去反驳他在历史区间上的观察，本质上是**用我选的口径否定他的问题** ——
> 这和 7.9 是同一个病灶：**答的不是他问的那个问题。**

### 7.24 ★ 前复权曲线的「增量」根本跑不到：份额段把 IP 打进了限流（2026-11-12 晚）

**触发**：第二次 CI（run 43202200187）跑完，`success`，但日志里价格段是这样：

```
价格：（增量 + 重叠校验）
  510050 近端失败 Remote end closed connection without response（旧数据保留）
  ... 10 只全部同样 ...
```

**「增量 + 重叠校验」一行都没执行到。** 十只全部死在第一跳「近端抓取」。
我上一版以为原因是「重试次数不够」，其实不是 —— 是**排队位置**。

**同一个接口、同样 5 次重试，同一次 CI 里两个结果**：

| 脚本 | 在 update.py 里的位置 | 结果 |
|---|---|---|
| `fetch_price_bfq.py` | 第 2 位 | **7/10** |
| `fetch_history.py` | 第 6 位 | **0/10** |

**真正的原因在中间**：`fetch_history.py` 内部先跑「份额回补」，
而那段是按**日历天**算缺口的：

```
日历天 2,507 天 − 已有 1,661 天 = 846 天「待补」
其中 716 天是周末，其余是春节/国庆
真实的缺口：0 天
```

于是每次运行都白打 846 次上交所请求（每次还带 5 重试）。
打完这一轮，同一个 runner 的 IP 紧接着去打东财 → 0/10。

**这是一个 bug 喂出另一个 bug**。日志上看是两件事（「份额回补 846 天」和「价格 0/10」），
实际是一条因果链，中间隔了 5 分钟和 800 多行日志。

**三处修法**：

**① 缺口按交易日算，不按日历天算**

```python
# 原来
days = [start + i 天 for i in range((end - start).days + 1)]   # 日历天
todo = [d for d in days if d not in hist]                       # → 846

# 现在（scripts/_td.py）
todo = _td.missing_trading_days(hist.keys(), start.isoformat()) # → 0
```

交易日从哪来？**从本地价格文件的日期集合反推**。
不用维护「每年更新的休市表」（漏一次少一天，而且永远不知道漏了），
价格文件里出现的日期**就是**交易所真实开市的日子，自带节假日、不会过期。
这是本项目第三次用「让数据自己说」。

**② 互不依赖的两步，顺序按「谁会污染谁」排**

价格段和份额段读写的文件完全不重叠（`prices.json` / `shares.json`），
谁先谁后不影响结果。既然不依赖，就该**让请求数少的先跑**：
价格段 10 次（增量模式），份额段最多几百次。

> **先跑 10 次的，它面对一个干净 IP；跑完再让份额段去消耗配额。**

**③ 时间口径统一到北京时钟**

`date.today()` 在 GitHub Actions 上是 **UTC 日期**。CI 在 UTC 10:38 = 北京 18:38，
平时看不出差别；但只要挪到 UTC 20:00 之后，`date.today()` 就会比北京日期**早一天**。
新增 `scripts/_td.py` 收口这件事：

```python
def bj_today():
    return bj_now().astimezone(BJ).date()   # ⚠ 必须 astimezone，不能只 .date()
```

⚠ `.date()` 那条注释不是洁癖：`datetime.now(BJ).date()` 本来是对的，
但只要有人把 `bj_now` 换成返回 UTC datetime（测试注入、将来改读系统时钟），
`.date()` 就会**安静地返回 UTC 日期** —— 又是一个「不报错但错一天」。

**实测对比**：

| | 修前 | 修后 |
|---|---|---|
| 份额回补请求数 | 846 次 | **0 次** |
| 价格段（同一次 CI 内） | 0/10 | 待验 |
| 页面末日期 | 永远 T-1 | 待验 |

### 7.25 ★ 「落后 1 天」是结构性永久状态，不是真落后（2026-11-12 晚）

这是 7.24 修完之后才露出来的第二层。

原来三个抓取脚本都写着：

```python
if p[0] >= today: continue      # 无条件丢弃当日
```

本意是防**盘中半日价**（见 11.x「盘中陷阱」，实测 10:21 抓到的成交额只有 8,486 亿，
是全天的 50%）—— 这个担心完全正确。

但把「今天已收盘」和「今天正在盘中」当成了同一件事：

| 时刻（北京） | 数据状态 | 旧代码 | 应该 |
|---|---|---|---|
| 10:21 | 半日量 | 丢弃 ✅ | 丢弃 |
| 15:00 | 刚收盘，未定稿 | 丢弃 ✅ | 再等 10 分钟 |
| **18:38（CI 实际运行时刻）** | **已定稿 3 小时 38 分** | **丢弃 ❌** | **采纳** |

**后果不是「偶尔落后一天」，是「每天都落后一天」。**
而这一条会被体检栏忠实地报出来，于是：
**页面天天挂一条琥珀色提示 → 三天后没人再看 → 真出事时也看不见。**

我上午刚在 `_fh.py` 里写下「周末必红的仪表盘会被当成噪音关掉」，
下午就在另一个文件里造了一条**每天必然为琥珀**的提示。同一个死法，换个地方。

**修法**：判据从「是不是今天」换成「**这一根定稿了没有**」

```python
CLOSE_HHMM = (15, 10)      # 15:00 收盘 + 10 分钟给定稿

def accept_day(d):
    if d < bj_today_str(): return True      # 昨天以前一定定稿
    if d > bj_today_str(): return False     # 未来日期 = 脏数据
    return today_allowable()[0]             # 今天看时钟
```

**放开当日之后，会不会把价格和份额的日期搞错位？**
会错位（价格到 11-12、份额只到 11-11），但**不影响计算**：
`compute_demo.py` 的 `days` 取自**份额日期**，价格只按 `days` 去查：

```python
days = sorted(d for d in shares if d >= START and '510300' in shares[d])  # 份额口径
p_q = [qfq.get(code, {}).get(d) for d in ds]                              # 按份额日期取价
```

所以价格多出来的那天不会被读到。**份额才是全站的时间轴，价格只是查表对象。**

### 7.26 三处「各自写一遍」的规则，改一处漏两处（2026-11-12 晚）

`>= today` 这条规则在 **3 个文件里各写了一遍**：
`fetch_index.py` / `fetch_price_bfq.py` / `fetch_history.py`。

上午修「盘中陷阱」时只改了 `fetch_index.py`（因为是在那个文件里发现的），
另外两处一直留着旧写法。这就是 7.25 那个 bug 能同时存在于三条抓取线上的原因。

同一天还有一次同型事故：`demo.html` 里 `line()` 和 `expandAll()` 各写了一遍
一模一样的行渲染（见 7.23 附近），改一处忘一处。

**规则**：一条规则如果要在 N 个地方生效，就把**判断本身**收进一个函数，
各调用方只负责调用。这次的容器是 `scripts/_td.py`。

⚠ 并且加了**回归测试**防止再犯（`tests/test_time_axis.py`，33 项断言）：

```python
bad = ('>= today' in body) or ('< TODAY' in body) or ('date.today()' in body)
chk(f'{fn} 不用「无条件丢弃当日 / 容器时区」写法', bad, False)
```

这条测试有个细节值得记：第一版直接对源码全文做 `in` 判断，
结果**注释里写的「原来这里是 x >= today」也被算成复发**，
于是测试奖励「把解释删掉」—— 修法是先剥掉注释再判断。


### 7.27 ★★ 体检栏报了「落后 0 天」，而实际是 9/10 停更（2026-11-12 深夜）

这是到现在为止**最该记住的一个**。它不是「坏了没报」，是**报了一个好听的假话**。

第五轮 CI 跑完，线上的真实状态是：

```
data/prices.json
  510050  末 2026-11-12     ← 1 只前进了
  其余 9 只  末 2026-11-11   ← 9 只停更
```

而页面体检栏显示：

```
价格（前复权，画曲线用）   2026-11-12 · 当日 · 1/10
```

读起来像「今天更新了，只是慢半拍」。**没有任何一个字是假的，但整句话的意思是假的。**

原因在这一行（`fetch_history.py`）：

```python
_last = max(v[-1][0] for v in prices.values() if v)
```

`max()` 取的是**最快的那一只**。只要有一只前进了，整项的 `last` 就被拉到最新，
`lag = 今天 − last` 直接归零，其余九只停更多久都算不出来。

> **一批数据的新鲜度由最慢的那部分决定，不是最快的。**

这和 7.24 / 7.25 是**同一个母题的不同变体**：
- 7.24：请求把自己打进限流（把「多打几次没坏处」当成真）
- 7.25：`>= today` 无条件丢弃当日（把「今天=盘中」当成真）
- 7.27：`max()` 当新鲜度（把「有一只新了=全都新了」当成真）

三次都是**用一个便利的写法替代了一次真实的度量**。

修法：`_fh.majority_last()`

```python
def majority_last(series):
    """一批序列里，**多数资产**停在哪一天。返回 (日期, 领先只数, 总数)。"""
    tails = [v[-1][0] for v in series if v]
    cnt = Counter(tails)
    for d in sorted(cnt, reverse=True):
        if cnt[d] * 2 >= total:          # 覆盖过半资产的那天
            ahead = sum(n for dd, n in cnt.items() if dd > d)
            return d, ahead, total
```

为什么**不取 min**（最旧的）：个别标的可能因停牌、上市晚而天生更旧，
取 min 会让整项永远显示陈旧，变成另一头的老狼来了。取「多数所在的那天」才对。

并且**必须把领先的那几只单独说出来** —— 否则那个最新日期仍然像是在给全体贴金：

```
价格（前复权）  2026-11-11 · 1/10	；9 只失败 …；1 只已到更晚一天（其余停在 2026-11-11）
```

同一个 `max()` 写法在 `fetch_price_bfq.py` 里也有一份（那天它 10/10 全成，
所以没暴露）。**两处一起改**，否则等哪天它部分成功，就会原样复发 —— 这就是 7.26。

⚠ 判据本身也要用真实数据验一次，不能只看单测：

```
按新逻辑，price_qfq 会上报：  last = 2026-11-11   领先只数 = 1   总数 = 10
旧逻辑 max() 会报:            2026-11-12
```
`11-12` 是 1 只、`11-11` 是 9 只 —— 新逻辑报 11-11，和实际一致。

新增 `tests/test_health_honesty.py`（16 项），并把**全部测试接进 CI**。
在此之前那 72 项断言只在我记得手动跑的时候才跑，
「一个不在 CI 里的测试，等于一份没人读的说明书」。


### 7.28 ★ qfq 恒 1/10 不是代码错，是排队位置 —— 拆 job 才是解法（2026-11-12 深夜）

`_net.py` 的请求账单第一次把这件事算清了。同一轮 CI 里打 `push2his.eastmoney.com`：

| 步骤 | 次数 | 结果 |
|---|---|---|
| `fetch_price_bfq` | 10 | **10/10** |
| `fetch_index` | 3 | **3/3** |
| `fetch_history`（第 6 位） | 48（其中 40 次是重试） | **1/10** |

同一个域名，**前 13 次全通，第 14 次起 0.6 秒就 RemoteDisconnected**。
也就是说这个域名的容忍度大约在十几条，而 `fetch_history` 轮到它时配额早被吃光。

在同一个 job 里继续调没有出路：
- 往前提？`bfq` 是核心数据（净流入靠它），不能让它吃亏；
- 降重试？治的是表象 —— 第一次就被拒，重试 0 次和 5 次都是 0/10。
  （这条我之前错了三次，见 7.24）

**解法：拆成独立 job。** GitHub Actions 的每个 job 跑在各自的 runner 上，
出口 IP 不同、配额各算各的。这不是调参，是**把共享资源变成独占资源**。

```
update  → fetch_etf / price_bfq / index / margin / dividend / shares / compute / build
qfq     → fetch_history --prices-only  （needs: update, if: always()）
deploy  → needs: [update, qfq],  if: always() && update success
```

三处必须一起改，少一处就漏：

1. `fetch_history.py` 加 `--shares-only` / `--prices-only` 两个互斥开关，
   拆成 `_fetch_prices()` / `_fetch_shares()` 两个函数。
   **不带开关时仍然是「两段都跑」** —— 本地手动回补的行为不变。
2. `update.py` 改成 `fetch_history.py --shares-only`
   （份额打上交所，另一个域名，不抢东财配额，留在主链没问题）。
3. `daily.yml` 新增 qfq job。

⚠ 一个**差点埋进去的竞态**：本来想并行（不写 `needs`）省几分钟，
但页面体检栏的数据来自 `compute_demo.py` 读 `fetch_status.json`，
而 `compute_demo` 跑在 update 里。qfq 并行的话，它写的状态会晚于 update 的
`compute_demo`，页面上就永远显示**上一次**的 qfq 状态 —— 又是一条静默的假话。
所以改成串行，并在 qfq 末尾**重算一次 + 重建页面**。

⚠ 同时给 `update` 的 push 加了 `pull --rebase --autostash` 重试 3 次：
以前这个分支只有一个 job 在推，现在两个 job 抢，`Updates were rejected`
会从偶发变常态。

**待验证**：拆 job 后 IP 是否真的独立 —— 第一次跑完要看两边的请求账单
是否都从 0 开始计数。这条不能靠「应该」，本项目因为「想当然」已经栽过三次。


### 7.29 ★★ 两个 job 各自生成构建产物 → 必然冲突，rebase 救不了（2026-11-12 深夜）

7.28 拆完 job 后第一次跑，update 全绿，qfq 也抓到了 5/10（原来是 1/10，
**拆 job 有效**），但 qfq 的提交挂了：

```
CONFLICT (content): Merge conflict in data/demo.json
CONFLICT (content): Merge conflict in demo_site.html
error: could not apply e71d747... data: 前复权价更新至 2026-11-11
第 1 次推送失败，重试…
第 2 次推送失败，重试…
第 3 次推送失败，重试…
```

结果：**qfq 抓到的数据一条都没进仓库**，页面上还是 update 当时的状态。

我当时的第一反应是「rebase 写错了」，于是加了个重试循环 ——
**方向完全错**。重试救不了：冲突没被解决，第 2、3 次连 `pull` 都进不去
（`Pulling is not possible because you have unmerged files`）。

真正的错在更上面一层：

> **`demo.json`（1344 KB）和 `demo_site.html`（1912 KB）是派生数据，
> 却让两个 job 各自生成一份，然后指望 git 把它们合并。**
> git 能合并「两边改了不同行」，合并不了「两边各自重新生成了同一个字符流」。

**规则：派生数据只能有一个生成者。** 一旦有两个，问题就不可解，
因为那不是冲突，是两份完整但不同的真相。

改后的分工：

| 环节 | 提交什么 | 生成什么 |
|---|---|---|
| `update` | 原始数据 + 构建产物 | 全部（它先跑，先把页面做出来） |
| `qfq` | **只有 `prices.json` / `fetch_status.json`** | 什么都不生成 |
| `deploy` | 不提交 | **统一重算一次 + 重建页面，然后发布** |

qfq 碰不到任何派生文件 → 不可能冲突。

⚠ 但这样又引出一个新问题，必须一起解决：qfq 只提交原始数据、不重建，
那么页面里内联的 `demo.json` 仍是 update 那时的（qfq 还没跑），
体检栏里「前复权」那一项会显示成**上一轮**的状态 —— 又是一条静默的假话。

所以 `deploy` 的第一步加了「重算 + 重建」：**deploy 是「所有数据都齐了」的那一刻**，
在这里算，体检栏 / 净流入 / 价格曲线读到的才是同一时刻的全量数据。
这也是把派生数据的生成**收敛到一个地方**的第 2 步。

⚠ 另一处同时改掉：`deploy` 拉数据从 `--ff-only` 改成 `--rebase`。
之前这个分支只有一个 job 在推，`--ff-only` 够用；现在两个 job 推，
两次 pull 之间就分叉了。

**这条教训的一般形式**（比这个项目本身更值得记）：

```
两个进程各自从同一份输入算出「完整结果」，再试图合并
→ 一定会失败，而且失败的方式是「丢一边」，不是报错。
唯一的解法不是合并得更聪明，是让其中一方根本不产生这个结果。
```


### 7.30 ★★ 第一版修法在 5:5 平局时仍然报「当日」，而且我的测试把 bug 写成了期望值（2026-11-12 深夜）

7.27 的修法上线后第一次跑，`price_qfq` 抓到了 5/10（拆 job 有效），
但体检栏还是 `last=2026-11-12 · 当日`。**一半数据停更，还是看不见。**

因为那天的真实分布恰好是 **5 只到 11-12、5 只停在 11-11 —— 平局**。
7.27 的第一版写的是「从新到旧找，第一个覆盖 ≥ 半数资产的日期」：
平局时先碰到 11-12（`5*2 >= 10` 成立）→ 报 11-12 → lag 归零。

改成**中位数（lower median）**：

```python
tails.sort()
d = tails[(total - 1) // 2]      # 不会偏向更新的一天
```

中位数在性质上保证「**至少一半资产不比它更新**」，所以永远不会高估新鲜度。

⚠⚠ **比 bug 本身更该记的是：为什么我的测试没抓住它。**

我当时写了 16 项断言，其中「场景 3」是：

```python
print('=== 场景 3：恰好一半一半 → 取较新的那天（不能因为平局就报旧）===')
chk('平局取较新的一天', last, '2026-11-12')      # ← 这就是 bug 本身
```

**我把 bug 写成了期望值。** 测试全绿，是因为它忠实守卫了一个错误的设计。

> 单测只能证明「代码符合我以为的样子」，
> 不能证明「我以为的样子是对的」。
> 判据不能只在脑子里推，必须拿真实数据跑一遍看结果。

补的测试：

- **场景 1b**：直接锁 5:5 这个真实分布，断言必须报 11-11、且如实报「5 只已到更晚一天」
- **场景 6b**：300 次随机分布的**性质检查** ——
  「不比报出日期更新的只数必须 ≥ 一半」。这条不依赖我举的例子对不对，
  它检查的是中位数的定义性质，属于「用性质代替样例」。

并且加了「更旧只数」的返回值：不光报出领先几只，也要报出**真停更几只** ——
只报前者会美化，只报后者会漏特例。

**最终线上结果（第八轮 CI，页面已核）**：

```
price_qfq   partial   last=2026-11-11  lag=1   got=5/10
   → 5 只失败 510880 515080 159915 159545…；5 只已到更晚一天
```

对比修复前：`last=2026-11-12 · 当日 · 1/10`。
**同一份数据，同一时刻，一句假话变成了一句真话。**

⚠ 一个遗留的小不一致：`deploy` 重算出的 `demo.json` / `demo_site.html`
**不提交回仓库**（这是 7.29 的代价），所以仓库里的 `data/demo.json`
会比线上页面旧一版。要知道线上到底是什么状态，应该看
`https://yrx00go.github.io/national-team-monitor/data/demo.json`，不是看仓库。
这条不是 bug，但**下次别拿仓库里的 demo.json 当线上现状**。


### 7.31 ★★ 东财 0/10 不是重试不够，是出口 IP 配额没了 —— 换源才是解法（2026-11-12 深夜）

第九轮 CI 的 `update` job 里，`fetch_price_bfq` **10 只全挂，0/10**。
前四轮我一直归因为「重试次数不够」「代码写错了」，这次拿到了请求账单，真相很直白：

```
fetch_price_bfq   push2his 50 次 → 0/10     ← 10 只 × 5 重试，每一次都是【首次即拒】
fetch_index       push2his  5 次 → 0/3
qfq               push2his 32 次 → 5/10     ← 同一时刻，另一个 job
```

关键在最后一行：**同一时刻，qn 那个 job 抓到了 5/10。**

如果是接口挂了，两个 job 该一起挂；如果是代码错了，两边用的是同一份逻辑。
唯一的解释是 **两个 job 跑在不同 runner 上，出口 IP 不同、配额各算各的** ——
这个 IP 那份配额根本没有了，重试只是在这个 IP 上多打 4 次，把自己往更深的坑里推。

> **重试是「把请求总量放大 5 倍」的乘数，不是「提高成功率」的乘数。**
> 在已经被限流的 IP 上，每一次重试都是一次新的拒绝。

所以这次的方向不是继续调重试、调顺序、调间隔 —— 那全在同一维度里打转。
**换成「保证今天这一根拿得到」这个问题，它的答案是不依赖单一 IP。**

**方案：加腾讯 fqkline 做备用源，只在东财失败时提供近端增量。**

先说可行性 —— 这一步必须实测，不能靠「应该差不多」：

| 代码 | 共同天数 | 完全一致 | 不一致 | 最大差 | 结论 |
|---|---|---|---|---|---|
| 510050 | 640 | 640 | 0 | 0.000000 | 口径一致 |
| 510300 | 640 | 640 | 0 | 0.000000 | 口径一致 |
| 510880 | 640 | 640 | 0 | 0.000000 | 口径一致 |
| 159915 | 640 | 640 | 0 | 0.000000 | 口径一致 |
| 512100 | 640 | 640 | 0 | 0.000000 | 口径一致 |

**腾讯 bfq 与东财 fqt=0 逐日比对 640 天 × 5 只，0 处差异，最大差 0.000000。**
两个源的不复权价就是同一个数，混源不会制造断层。

（对比：前复权两个源会差一个分红额，所以 **qfq 那边不能这么干**。同一个「混源」动作，
不复权能做、前复权不能做，区别就在「历史会不会被改写」。）

再说边界 —— 腾讯的硬上限是 **641 根**（请求 640/641/1000 都返回 641，传 2500 直接
TypeError），只能回溯到 2024-03 左右。本项目要 2020 年起的 ~1900 根：

**腾讯做不了全量回补，只能兜「今天这一根」。**

所以分工必须写死：

| 源 | 定位 | 能力 | 用在哪 |
|---|---|---|---|
| 东财 push2his | 主力 | 可回溯上市首日，能全量 | 永远先试它 |
| 腾讯 fqkline | 兜底 | 硬上限 641 根 | **仅在东财失败、且只需增量时** |

⚠⚠ **为什么「需要全量时绝不兜底」这条必须写进代码而不是靠自觉**：

腾讯硬补全量 → 得到「起点是 2024-03」的残缺序列 →
而 `need_full` 的判据是「起点 > 2020-01-02 就重抓」→ 永远成立 →
**每天重抓、每天得到同一段残缺数据，死循环且不自知。**

这种坑的特征是：日志一片绿（每天都「成功」），数据永远是同一段，
而你只会觉得「怎么总是在补历史」。宁可如实报失败、沿用旧价。

**实现上有一处刻意的做法：把「抓一只标的」从 `main()` 抠成函数。**

```python
def acquire(code, mk, have, fetch_fn=None, tx_fn=None):
    """返回 (fresh, src, err)，src 为 '东财' / '腾讯' / None。"""
```

理由不是「代码整洁」，是**可测性**：兜底分支的触发条件是「东财失败」，
而 CI 上东财有时通有时不通 —— **东财一通，兜底那段代码就永远不执行。**
一段从未被执行过的错误处理，和没有错误处理是一回事，只是更让人安心（＝更危险）。
把两个源做成可注入参数，就能在离线测试里把每种失败组合都真跑一遍
（`tests/test_tx_fallback.py`，36 项）。

**顺带自查出两个问题，都是真问题：**

**① 腾讯「接通」≠「给了今天的价」。**

兜底成功、但腾讯返回的末日期还是旧那一天（源本身滞后）→ `merge` 新增 0 根。
这一只会被算成**成功**（不在 `bad` 里），而 note 里写着「走腾讯备用源」——
**读起来像「有备用所以没事」，实际是「换了个源，今天这一根照样没拿到」。**

比彻底失败更误导，因为它看起来是绿的。这正是 7.27 那类静默失败的翻版：
不是「没拿到」，是「没拿到但报告说拿到了」。

改成两类分开计：

```python
if n_add > 0:
    tx_codes.append(code)      # 真帮忙了
else:
    tx_stale.append(code)      # 接通了，但末日期没前进
```
上报文案也从「N 只走腾讯备用源」改成
「N 只腾讯接通但末日期没前进（仍无当日）」。

**② 全失败分支里有个死分支。**

原来写的是 `if tx_codes: note += '（东财与腾讯备用源均失败）'`。
但全失败意味着 `out` 为空 → `tx_codes` 必定为空 → **那句话永远不触发**。
等于写了一段永远不会跑的提示。改成检查 `bad` 里有没有腾讯的痕迹。

> 一个判断条件如果恒为假，它看起来像「防御性代码」，
> 实际上什么都没防。**测不到的分支等于不存在的分支。**


### 7.32 ★ 一批数据的新鲜度由「中位数」决定，不由最慢的那只决定 —— 但也不由最快的

（这是 7.27 / 7.30 的最终结论沉淀，写在这里因为它是**通用规则**。）

这一轮在三个不同的地方碰到了同一个问题：`_fh.majority_last()` 该怎么取。

| 取法 | 结果 | 问题 |
|---|---|---|
| `max()` | 最快的 | **一只前进，整批就当当日** → 7.27 |
| `min()` | 最慢的 | 一只停牌（上市晚／停牌）就永远显示陈旧 → 老狼来了 |
| 覆盖 ≥ 半数 **取较新** | 偏向新的 | 5:5 平局时报当日 → 7.30 |
| **lower median** ✅ | 中间那个 | 性质上保证「至少一半不比它更新」，**永不**高估 |

```python
tails.sort()
d = tails[(total - 1) // 2]      # total 为偶数时取下中位，不偏向更新的一天
ahead  = sum(1 for x in tails if x > d)   # 领先几只，写进 note
behind = sum(1 for x in tails if x < d)   # 真停更几只，也要报
```

关键是**同时返回 ahead 和 behind**：
只报「领先几只」会美化（看不到还有一半停更），只报「停更几只」会漏掉特例。

这个函数现在在**四处**被调用，下面每一处原来都是独立的错，改的时候必须一起改
（这正是 7.26 的母题）：

- `fetch_price_bfq.py` 上报段
- `fetch_price_bfq.py` **全失败分支**（同一文件里第三处 `max()`）
- `fetch_history.py` 上报段
- `fetch_history.py` 兜底找不到 WATCH 时的分支


### 7.33 ★★ need_full 把「上市晚」当成「数据缺」—— 每天都在全量重抓、每天失败（2026-11-12 深夜）

这是 7.31 落地后第十轮 CI 用真实日志打出来的，而且**它本来就在跑，我此前一直没看见**。

`need_full` 的判据原来是「历史起点 > 2020-01-02 → 全量重抓」。听着合理，
但有两只是这样的：

| 代码 | 名称 | 上市日 | 起点 | 结果 |
|---|---|---|---|---|
| 588000 | 科创50ETF | 2020-11-16 | 2020-11-16 | 起点**天生**晚于 2020-01-02 |
| 159545 | 中证红利低波 | 2024-04-15 | 2024-04-15 | 起点**天生**晚于 2020-01-02 |

它们不可能更早。于是**每天**都被判成「需要全量」→ 每天重抓 ~1900 根 →
每天失败 → 体检栏天天写「2 只未获取」。

> 一条永远亮着的琥珀色提示 = 没人再看 = 等于没装。

讽刺的地方在于：我当天上午刚在 `acquire()` 的注释里写下
「硬用腾讯补全量会变成**死循环且不自知**」，晚上就发现这个死循环**本来就在跑**，
只是我把它写成了「别人可能会犯的错」。

**判据要分开两种情况：**

```
起点晚，是因为数据缺   （该补）→ 全量
起点晚，是因为它上市晚 （补不到）→ 增量
```

区分办法：记住「这只最早一次能拿到哪天」。既然每次全量都是从
`BEG`（2019-01-01）请求的，那拿回来的最早日期**就是**它的真实上市日，
再请求也不会更早。

实现上与 `prices_bfq.json` 分开存一个 sidecar：

```
data/listing_first.json    {code: "最早拿到过的日期"}
```

⚠ 为什么不塞进 `prices_bfq.json`：那个结构 `compute_demo.py` 在读，
往里加字段会牵连下游。**派生数据文件的结构一旦被下游依赖，就不要为了省一个文件去改它。**

测试里直接拿仓库真实的 10 只验：「仍在需全量的」必须为空：

```python
_still_full = [c for c, v in _px.items() if v and m.need_full(v, _first.get(c))]
chk('★ 真实 10 只里仍在「需全量」的只数', _still_full, [])
```

这条比任何构造的例子都硬 —— 它锁的是此刻仓库里的真实状态。

**★ 而且它在对面那条链路上也有一份。** 我修完 bfq 之后才去看 qfq 日志，
`fetch_history.py` 第 238 行是同一个判据的复制品，两只同样天天「失败」——
日志里看着像「东财又掐断了」，实际是**我们在要求一件拿不到的事**，
掐断只是让它必然失败。

两条链路共用 `data/listing_first.json`（不各存一份，否则必然有一天不一致，
而表现就是「一条链路正常、另一条天天失败」，极难和二为一）。

**修完的实测对比（同一份代码，前后两轮 CI）：**

| | 修前 | 修后 |
|---|---|---|
| qfq 成功只数 | 4/10 | **10/10** |
| qfq 请求次数 | 34 次 | **10 次** |
| qfq 失败只数 | 6 | **0** |

一个判据同时解决了「天天失败」和「白烧配额」。
而且它反过来证明了一件事：**东财并没有变宽容，是我们不再要求一件拿不到的事；
请求量一降，掐断也跟着消失。**


### 7.34 ★ 判「备用源有没有帮上」，不能看「新增了几根」（2026-11-12 深夜）

7.31 的兜底落地后，我加了 `tx_stale` 用来区分「腾讯接通了但没帮上」。
第一版判据是：

```python
if n_add > 0:  tx_codes.append(code)      # 带来了新数据
else:          tx_stale.append(code)      # 没帮上
```

第十轮 CI 立刻打脸，7 只全被误报：

```
510050 增量 +0 根（旧 1906 根保留） → 末 2026-11-12  [东财]
510300 增量 +0 根（旧 1906 根保留） → 末 2026-11-12  [腾讯]
510300 东财失败 → 腾讯兜底（末日期没前进，没帮上）    ← 假警报
```

**旧数据本来就已经到 11-12**，腾讯也返回到 11-12，`merge` 自然新增 0 根。
这不是「没帮上」，这是「本来就有、现在确认还在」。

又是一条每天必亮的假警报 —— **7.25 那个死法的第四次复发**。

**正确判据是比日期，不是数根数：**

| 比较 | 含义 | 该报什么 |
|---|---|---|
| `fresh 末 > have 末` | 带来新数据 | 正常 |
| `fresh 末 = have 末` | 持平，数据无损失 | **正常，不该报警** |
| `fresh 末 < have 末` | 比手里的还旧 | 本次兜底无效 ← 只有这种才该报 |

```python
if fresh[-1][0] < have[-1][0]:
    tx_stale.append(code)
```

> **「新增 0 根」是一个双义词**：可能是「源也是旧的」，也可能是「早就有了」。
> 用双义词当判据，报警就必然一半是假的。
> **判据要问「和昨天比是好是坏」，不要问「今天有没有动」。**


### 7.35 ★ 指数也能兜底：但只能兜「当日一根」，且必须两样一起兜（2026-11-12 深夜）

`fetch_index.py` 在 CI 上连续多轮 **0/3 全挂**，上证点位和两市成交额天天不更新。
它产出的正是「净申赎 × 大盘位置」那张叠加图的**位置轴** ——
不更新，那张图就等于在骗人。

腾讯能兜，但能力和 bfq 那边**不一样**，这个差别决定了实现方式：

| 能给什么 | 腾讯指数接口 |
|---|---|
| 历史点位序列 | ✅ 有（`day` 键，640 根） |
| 历史成交额序列 | ❌ **只有当日快照**（`qt` 里一个 `价/量/额` 三合一字符串） |

所以**不能只兜点位**：会出现「点位到 11-12、成交额停在 11-11」的半截状态，
比整体沿用旧值更难跟人解释。**要么两样都有，要么整体不用。**

口径已实测对齐（同一交易日）：

| 项 | 东财（历史） | 腾讯（快照） |
|---|---|---|
| 上证点位 | 3655.83 | 3655.83 ✅ |
| 两市成交额 | 19,320.8 亿 | 8,795.4 + 10,525.4 = **19,320.8 亿** ✅ |

精确到最后一位。所以兜底不会在序列上留断层。

**实现上有两个刻意的选择：**

**① 三处失败分支共用一个 `_apply_snapshot()`。**

东财失败有三种样子：抛异常、返回空、只返回当日盘中数据。
三种对使用者是同一件事——「今天没有」。所以三处都要兜底。

但写入逻辑**不能各写一遍**（7.26 的母题：改一处漏两处）。

**② 只追加，不覆盖。**

```python
if not seq or snap['date'] > seq[-1][0]:
    seq = seq + [[snap['date'], ...]]
```

实测验证：本地跑这一轮时旧数据已经到 11-12，腾讯快照也到 11-12，
`>` 判断拒绝追加 → **文件一根没变、一个值没覆盖**。这正是想要的行为。

**本地实跑（东财对这台机器的 IP 已完全封死，所以必然走兜底）：**

```
上证指数抓取失败：RemoteDisconnected: ... → 试腾讯快照
  ✓ 腾讯快照兜住当日：2026-11-12  上证 3655.83  两市成交额 19,320.8 亿
  [请求账单] 共 7 次　push2his.eastmoney.com 5 次　web.ifzq.gtimg.cn 2 次
```

这条路径在本地是**真的被执行**的，不是「写完就等 CI」——
这也是这一轮学到的最要紧的一条（见 7.36）。


### 7.36 ★★ 改了但从没跑过 —— 这一轮所有问题的共同来源（2026-11-12 深夜）

回头数这一轮的六个 bug，它们的共同点不是「写错了」，而是**写的东西从来没被执行过**：

| 问题 | 为什么没被发现 |
|---|---|
| 7.27 `max()` 当新鲜度 | 只有部分成功时才出错，而当时天天全成功或全失败 |
| 7.29 两个 job 各自生成构建产物 | 只有一个 job 能推成功的那些天不会冲突 |
| 7.30 5:5 平局仍报当日 | 那天恰好是平局，**而我的测试把 bug 写成了期望值** |
| 7.31 兜底分支 | 东财一通，它就不执行 |
| 7.33 上市晚被判成需全量 | 它**每天都执行**，但失败被当成「正常的部分失败」 |
| 7.34 `n_add` 判据 | 同上，误报被当成「兜底没帮上」 |

**两条对策，都已经落地：**

**① 把分支抠成可注入的纯函数，让它能被离线跑到。**

```python
def acquire(code, mk, have, fetch_fn=None, tx_fn=None, first_ever=None):
```

一段从未被执行过的错误处理，**和没有错误处理是一回事**，只是更让人安心。
`tests/test_tx_fallback.py`（40 项）能把「东财必挂 / 腾讯也挂 / 需全量」每种组合跑一遍。

**② 给工作流加 `push` 触发。**

原来只有 `schedule` + `workflow_dispatch`：

```yaml
on:
  schedule: [...]
  workflow_dispatch: [...]
  # ↑ 推送代码不触发任何运行
```

意味着每次改完都得**记得**手动 dispatch，忘一次就等于「改了但从没跑过」。

```yaml
  push:
    branches: [main]
    paths:
      - 'scripts/**.py'
      - 'tests/**.py'
      - '.github/workflows/daily.yml'
```

只在动代码/测试/工作流时触发，改 README 不触发，免得白烧配额。

> **「我改好了」和「它真的跑过了」之间，差着一个必须存在的步骤。
> 少了这一步，所有验证都只是在读自己的代码。**

### 7.37 ★ 卡片写「当日」，等于没给时间坐标（2026-11-13）

用户一句话：**「当日流入估算，改成具体日期，比如 11.12 日流入估算」**。

看起来是改四个字，实际上暴露的是**这个站上「当日」是个双义词**：

| 数据 | 什么时候有 | 卡片上自称 |
|---|---|---|
| ETF 份额（算净流入用） | T+1 披露，通常 T+1 下午 | 「当日」 |
| 两市成交额 | 当晚就有 | 「当日」 |
| 两融余额 | T+1 晚间 | 「当日」 |

三样东西**各差一两天**，卡片上却都叫「当日」。所以「当日」到底是 11-12 还是 11-13，
**光看卡片判不出来** —— 你只能去翻代码才知道它读的是 `latest_date`。

更要命的是**连带误读**：旁边三格（5日 / 20日 / 成交额）各自对应不同日期，
一旦有人把「当日」理解成「今天早上」，就会把**昨天**的流入当成今早的消息。

**改法：数字对应哪一天，就写在卡片上。**

```
11.12 估算净流入        -126.4 亿
11.6–11.12 累计         -147.3 亿
10.16–11.12 累计       +2069.0 亿
两市成交额   11.12 · 5日均 … · 一年分位 …
```

**两个不那么显然的点：**

**① 区间必须数交易日，不能数日历天。**

第一版我想的是「`latest_date` 往前推 5 天」，直接踩坑：

```js
// ✗ 错的：11-12 往前推 5 个自然日 = 11-08
//   而 11-07 / 11-08 是周末，区间里实际只有 3 个交易日
```

正解是取 `flow` 序列自己的日子：

```js
const a = mdShort(ds[ds.length-n]), b = mdShort(ds[ds.length-1]);
// ds = D.days，与 combo.flow 一一对应（compute_demo.py:1145）
```

`days` 是按交易日排的，`days[length-n]` 天然就是「n 个交易日之前」。
实测 `11.6–11.12` 正好含 11-07/11-08 那个周末，共 5 个交易日 —— 这是对的。

**② 成交额那格必须显示自己的日期。**

它用的是 `volume` 自己的最新一天（`vLast.d`），**不一定是 `latest_date`** ——
成交额当晚就有、份额要 T+1。所以这一格单独写 `${mdShort(vLast.d)}`，
否则会和左边两格看起来同一天，实际差一两天。

**降级：拿不到日期退回「当日」/「近 N 日累计」，不留空。**

留空会变成一张**没有时间坐标的卡片**，那比用相对词更糟 ——
至少「当日」还提示了「这不是历史值」，空白什么都没说。

**测试（`tests/test_kpi_date_label.py`，20 项）里有一条值得单独说：**

```python
# 我原来写的：
chk('★ template 里没有拿日期做减法',
    bool(re.search(r'latest_date[^\n]*-', tpl)) and 'new Date(' in tpl, False)
```

前半恒 `False`，`and` 之后整条**恒通过** —— 看起来在测，实际什么都没测。

改成在 `spanTag` 函数体里查禁用词，并**反向验证**：故意插入
`t.setDate(t.getDate()-n)` → 测试准确变红并指出 `['new Date','setDate','getDate']`。

> **新写的断言必须故意插一段错误代码看它变不变红。
> 不会变红的断言不是测试，是装饰。**

**顺带修掉的：`test_index_fallback.py` 把「收盘后」当成了永远成立的前提。**

原断言写死「成交额 > 12000 亿」，11-13 上午 09:39 跑时腾讯只返回 2,821 亿
（半小时量），直接变红。**这不是代码错，是断言的时间前提错了。**

改成分两种情形：

```python
settled = m._td.accept_day(snap['date'])
if settled:  chk('已定稿 → 成交额是两市之和（>12000 亿）', snap['turnover'] > 12000, True)
else:
    chk('盘中 → 成交额 >0', snap['turnover'] > 0, True)
    chk('★★ 盘中快照必须被 accept_day 拒绝（不写入序列）',
        m._td.accept_day(snap['date']), False)
```

最后那条才是真正的重点：**盘中半天量绝不能被当成定稿数据写进序列。**

**顺带删掉 `index.html`（2026-11-13）。**

它是早期 GitLab Pages 时代留下的副本（1,979,593 B），
两份 CI 都是 `cp demo_site.html → index.html` 现生成，根目录这份**无人引用**
（`grep -rn "index\.html"` 在 `*.py` / `*.sh` / `*.html` 里零命中）。

留着它的唯一效果是：**每次改模板，它都会变成一份过期的假页面**，
而且里面还带着旧的「当日估算净流入」—— 正好呼应
「html 只留必要的内容，非必要不要放着」。

现在仓库根目录只有两个 html：`demo.html`（模板）+ `demo_site.html`（产物）。

### 7.38 ★★ 尺子选错，量出来的数就一定错 —— 「落后 1 天」是怎么误报的（2026-11-13 上午）

7.37 上线后不到半小时，用户又发来一张截图，指着体检栏说：

> **「这个也不算落后，现在是 11.13 号的上午，我们本来也是 11.13 号晚上才更新当天的内容」**

截图上是：

```
数据体检 · 2 项需要注意
✕  上证指数 / 两市成交额   2026-11-12 · 落后 1 天    接口主动断连…
!  价格（前复权）          2026-11-12 · 落后 1 天    9/10 · 1 只失败 159919
```

**他完全正确。** 11-13 09:52 时，11-13 的收盘价根本还不存在（15:00 才收盘）。
拿 11-13 当尺子去量 11-12 的数据，量出「落后 1 天」是必然的 ——
**而那个「落后」在现实里不存在。**

#### 根因：两个概念共用了一个变量

```python
# 原来
lag = (今天 - last).days          # 今天 = 真实日历今天
days_silent = (今天 - at).days    # 同一把尺子
```

`今天` 被用在两处，但两处问的是**完全不同的问题**：

| 用它算什么 | 该用什么尺子 |
|---|---|
| 「脚本多久没跑了」 | **真实日历今天**（周末没跑也是没跑） |
| 「数据落后几天」 | **数据本该已经到了的最近一天** |

上午 09:52 时，第二个问题的答案是 **11-12 而不是 11-13**。
用 11-13 去问，等于责怪数据没提前告诉你收盘价。

而且单位也错了：`(今天 - last).days` 数的是**自然日**。
周五的数据周一来看是 3 天，可中间只过了一个交易日。

> **同一个变量名底下藏着两个语义，是这类 bug 最常见的形态。
> 它不会报错，只会在特定时刻（每天早上、每个周一）安静地说错话。**

#### 修法：拆成两个参数，各自一个出口

`_td.expect_asof()` —— 全站唯一回答「数据该到哪天」的地方：

```python
if today_allowable()[0]:      # 今天已收盘定稿
    return 今天                 #   → 今天的数据该有了
prev = 交易日历里 < 今天的最后一个
return prev                    # 否则退到上一个交易日
```

`_td.trading_gap(a, b)` —— 数**交易日**而不是自然日。

`_fh.summarize(today=…, asof=…)` 里两个参数分开用：
`today` 只喂 `days_silent`，`asof` 只喂 `lag`。

#### 更隐蔽的一处：失败 ≠ 落后

改完基准日，「落后 1 天」没了，但 ❌ 和 ! 两个图标还在，标题还是「2 项需要注意」。
因为 11-13 凌晨 01:44 那次 CI 确实失败了（东财拒绝、腾讯快照也不可用）。

**可那次失败根本没有「该抓而没抓到」的东西 —— 它跑得太早了。**

所以状态判定的判据也要换：

```python
# 不是「这次抓成功了吗」，而是「数据落后了吗」
if state in ('fail', 'partial') and lag == 0:
    state = 'ok'
    note = f'本次未抓取成功（数据已是最新 {last}，无需更新）；' + 原note
```

这样不会掩盖真问题：东财连挂五天 → `last` 追不上 `asof` → `lag > 0` → 照样红。
**只有「本来就没得抓」才不再报警。**

#### ★ 修复时差点又埋一个雷，而且在真出事时才会炸

`trading_gap` 头一版直接用 `trading_days()`（交易日历）。
但那个日历是**从已有价格文件反推的** ——

```
抓取全挂一个月 → 价格文件停在 11-12 → 日历末位也停在 11-12
→ 拿 12-10 当基准日数交易日 → 日历里没有 11-12 之后的日子
→ 数出 0 天 → 落后一个月，体检栏报「已是最新」
```

**这比误报「落后 1 天」严重得多：那是多报，这是瞒报。**
而且它恰好只在「真出大事」时触发，平时完全看不出来。

修法：日历覆盖不到的部分退一步按工作日估。误差只有「这段里的法定节假日会被多算」，
但那段本来就是异常区间 —— **多算几天远好于报 0 天**。

测试里专门有一条守着这个（`场景 12`）：把基准日推到一个月后，必须变红。

#### 顺带改掉的文案

| 原来 | 现在 | 为什么 |
|---|---|---|
| `2026-11-12 · 当日` / `· 最近交易日` | `2026-11-12 · 已是最新` | lag=0 已表示「已是最新」，再注解「当日」等于让人猜是哪天 —— 正是 7.37 刚修掉的病 |
| `落后 N 天` | `落后 N 个交易日` | 单位是交易日，写「天」会让人以为漏了 N 天行情 |
| `7 项数据均按时更新` | `7 项数据均按时更新（今日行情晚上更新）` | 「已是最新」之后的新疑问是「为什么不是今天」，说明白比让人猜强 |

#### ★ 这一轮的验证纪律

新增 `tests/test_lag_baseline.py`（33 项），并且**三条断言都做了反向验证**：

| 故意插入的错误 | 测试反应 |
|---|---|
| `lag` 改回自然日差 | 2 项变红，准确指出「真落后 5 个交易日」走了 1 |
| 删掉「失败但没落后 → ok」的降级 | 4 项变红，全部指向那两条误报 |
| `trading_gap` 不数日历之外的日子 | 3 项变红，包括「落后一个月必须报 stale」 |

最后用 node 跑真实渲染，确认上屏文字：

```
修复前   数据体检 · 2 项需要注意
         上证指数 / 两市成交额 失败（落后 1 天）

修复后   数据体检 · 全部正常
         7 项数据均按时更新（今日行情晚上更新）

真落后时  数据体检 · 1 项需要注意        ← 照样报警，且自动展开
         上证指数 / 两市成交额 失败（落后 3 个交易日）
```

> **「不误报」不等于「不再报」。这两件事的验收标准完全不同：
> 前者看每天早上是否安静，后者看真出事时是否响亮 —— 两条都得测。**



## 八、机构存活率：一个不需要猜的证明

```
存活率 = 当前总份额 ÷ 历史峰值期机构持有份额
```

**< 100% 时是数学结论，不是推断**：今天的总份额里装着所有人（机构+散户+做市商），
如果这个总数已经少于峰值期机构**单独**持有的量，那机构无论如何都净卖出了，
且卖出比例不低于 `1 − 存活率`。不需要知道是谁在卖、也不用猜动机。

| 代码 | 名称 | 峰值期机构持有 | 当前总份额 | 存活率 | 至少卖出 |
|---|---|---|---|---|---|
| 510050 | 50ETF | 2025-06 · 523 | 168.2 | **32.2%** | 67.8% |
| 510300 | 300ETF华泰柏瑞 | 2025-06 · 819 | 463.4 | **56.6%** | 43.4% |
| 510500 | 500ETF南方 | 2025-12 · 166 | 96.3 | **58.1%** | 41.9% |
| 512100 | 1000ETF南方 | 2025-12 · 244 | 193.1 | **79.2%** | 20.8% |
| 159919 | 300ETF嘉实 | 2025-06 · 398 | 139.6 | **35.1%** | 64.9% |
| 588000 | 科创50ETF华夏 | 2023-12 · 200 | 1076.3 | 538.3% | — |
| 510880 | 红利ETF华泰柏瑞 | 2024-12 · 35 | 59.2 | 169.2% | — |
| 515080 | 中证红利ETF易方达 | 2026-06 · 26 | 71.1 | 275.9% | — |

**这个证明的边界必须说清**：它只能**证明卖出**，不能**证明没卖**。
存活率 >100% 只说明份额总量还在扩张，机构可能一边卖一边被新增申购填上 ——
要判断科创50 / 红利这类扩张型标的，得看下一期半年报的机构占比有没有掉。

### 9.8 ⚠ 但「买回来」不等于「增量资金进场」—— 两融那边有笔账对得上（2026-11-12 补）

上面 9.7 的数字是真的，但**把它读成「新钱来了」是错的**。加了两融数据之后才看清：

| 口径 | 2026-06-25 高点 | 2026-11-11 | 变化 |
|---|---|---|---|
| 两融余额 | 30,330 亿 | 23,023 亿 | **−7,307 亿（−24.1%）** |
| 其中近 20 日 | — | — | **−2,328 亿** |
| 同期 ETF 净流入（近 20 日） | — | — | **+2,299 亿** |

**两个数几乎完美对冲（差 29 亿，1.3%）。** 这不是巧合能解释的量级。

所以 9.7 那波流入，更可能的解释是 **同一批钱换了载体**：
从**带杠杆的个股仓位**，换成**不带杠杆的宽基 ETF**。
融资盘撤出 2,328 亿、ETF 进来 2,299 亿，全市场总敞口基本没变，只是杠杆降了、波动结构变了。

**这个区别为什么重要：**

| 读法 | 推论 | 对操作的含义 |
|---|---|---|
| ❌ 「增量资金进场」 | 有场外新钱，看好后市 | 可以更乐观 |
| ✅ 「存量换载体」 | 没有新钱，只是风险偏好下降 | **不该更乐观，该更谨慎** |

同期两个分母都在历史低位：**两市成交额一年分位 12%（缩量）**；
**杠杆水位则以「占流通市值」看是偏高（2.49%，2018 年以来 86% 分位），
方向在退（20 日 −2,328 亿）** —— 注意这里不能写「两融一年分位 2%＝杠杆低」，
那个口径是错的，详见 11.4.1。
「份额在涨、场子在冷、杠杆偏高但在撤」这个组合，典型含义是
**承接方是少数大资金，不是市场情绪转暖**。

⚠ 需要说清楚的边界：这两个数**对得上不等于因果关系成立**。
可能是同一批钱，也可能是两批钱恰好规模相近。但无论哪种，
「增量资金大举进场」这个说法**都缺乏支持** —— 因为净敞口没增加。
详见「十一之四」和页面上的「量能与杠杆」面板。

### 9.9 这件事对「倍量」算法的意义

这恰好证明那个号的框架有用，但也暴露了它的缺陷：
**用固定分母算倍量，根本看不见这种量级的变化。**
如果分母用 2025 年末份额，今年 1 月这波 −89% 会把指标拉到负无穷，

不是「每天看国家队买了多少」，而是：

## 十、股息率模块（已与本地自有脚本交叉验证）

参考实现：本地另一个已运行多年的 `alert_my_dividend/` 脚本

它只保留**当天快照**（`.dividend_cache.json` 只有一个日期），画不出历史曲线。
所以本站按原口径**重算**，而不是搬数据：

```
股息率(%) = 年化每股分红 ÷ 股价 × 100
年化每股分红 = 最近一个完整财年的两次派息之和，按【报告期】配对
```

**为什么不能按「近 12 个月除权日求和」**：2025 年起银行改成中期+年度两次派息，12 个月窗口会装进 3 次。
实测工商银行按除权日求和得 0.4614 元 → **5.37%**；按报告期配对是 0.1689 + 0.1511 = 0.3200 元 → **3.73%**。后者才是年化。

**历史曲线无未来函数**：对每个历史日期 t，只用 t 时刻已除权的分红重新配对，而不是拿今天的分红回填 2024 年。

**交叉验证**：11 只标的当前股息率与本地缓存最大偏差 **0.05 个百分点**（差异来自盘中价 vs 收盘价）。

### 7.13 双轴图零点错位：用户投诉「金额和纵坐标对不上」，他是对的（2026-11-11）

**现象**：用户指着「每日估算净申赎」那张图问 ——

**他圈对了。** 这不是读数错误，是我的设计缺陷：

```
单日净流入 flow: −596.4 ~ +488.8   跨度 1085.2 亿
区间累计   cum : −1949.8 ~ +6862.9  跨度 8812.7 亿
量级比（跨度）: 8.1 倍
```

**追记（同日晚上，用户第三轮反馈后自我修正）**：
上一段把一个**手段**当成了**结论**。「不要双轴」不是目的，「读数不会错」才是目的。
真正的根因是「两根轴各自自动缩放，零点落在不同高度」——
只要**需要零点的那根轴 `beginAtZero`**，或者**两根轴都不需要零点**，双轴就是安全的。

修订后的判据：
1. 两个序列是否有**各自独立的信息**？先算相关系数，>0.95 就别画两条。
2. 需要零点的量（金额、份额、水位这类「有/无、进/出」的量）→ 那一根轴必须 `beginAtZero`。
3. 不需要零点的量（价格、点位、比率这类「位置」量）→ 让它自动缩放，否则白白浪费一半绘图高度。
4. 若两根轴都需要零点 → 必须两轴都 `beginAtZero`，并**实测零点像素差 = 0**（单只页就是这么做的）。
5. 若一根需要一根不需要 → 零点必然不重合，此时**靠标注消歧**（legend／轴标题／刻度颜色），不靠对齐消歧。

**全部精确吻合，误差 0**。数据从来没坏。

真正的解释很朴素：**1660 个交易日的日线挤在 ~1150px 宽里，每根占不到 0.7px**。
这不是噪声，是真实的高频波动被横向压缩后的必然外观。
单日 |涨跌|>3% 的有 24 天、>5% 的有 6 天，最大 2024-09-30 的 +8.06% —— 全是真实历史。

**错在哪**：把「图看起来不对劲」直接翻译成「数据错了」，跳过了「换个尺子看会不会就对了」。
**判据：怀疑数据之前，先算一次「这个视觉畸变需要多少倍的横向压缩才会产生」。**
数据要错，错的往往是量级（差 10 倍、差 100 倍），而不是「抖得比记忆中多」。

修法不是改数据，是改**呈现**：线宽 1.7 → 1.3px。相邻两天的笔画不再在垂直方向叠起来糊成一片橙雾。

### 7.15 年份刻度写了 `label` 却不生效，`afterBuildTicks` 被覆盖（2026-11-11 晚）

在 `afterBuildTicks` 里给 tick 设了 `label:'2020'`，图上仍显示 `2020-01-02` ——

### 7.16 整页白屏：`const V` 重复声明（2026-11-12）

新写的量能面板里用了 `const V=D.volume`，而文件顶部已经有
`const V = JSON.parse(document.getElementById('DIVI').textContent)`（股息率页的数据对象）。

**两个 `const V` 在同一个顶层词法作用域 → 整个 script 块 `SyntaxError` → 全站不执行 → 白屏。**

排查过程（记下来是因为下次还会遇到）：

| 步骤 | 现象 | 结论 |
|---|---|---|
| 1 | 探针读 `#kpis .kpi` 得 0 个 | 不是「渲染错」，是「根本没渲染」 |
| 2 | 探针读 `window.charts` 得 `undefined` | 主脚本整个没跑 |
| 3 | 把 `<script>` 块抽出来 `node --check` | **`SyntaxError: Identifier 'V' has already been declared`** |

⚠ **教训一：浏览器不会为「整块脚本语法错误」弹出任何可见错误**，
`window.onerror` 也抓不到（语法错误发生在解析阶段，早于执行）。
所以页面上那个收集 `ERRS` 的数组**在语法错误时永远是空的** —— 不能拿它当「没问题」的证据。
**必须抽出来做静态检查。**

⚠ 教训二：这类错误的特征是「**改了 A 功能，B 功能也坏了**」。
本次是「加量能面板，结果连主图都没了」。看到「完全不渲染」要先怀疑语法/加载，
不要顺着功能逐个 debug。

⚠ 教训三：`node --check` 是这里唯一可靠的手段，成本 2 秒。**改完 JS 就该跑，不要等到截图白屏才发现。**

同类风险：`V` / `D` / `c` / `L` / `T` 这类单字母名在本文件里都已被占用，新代码一律用两字母以上。

### 7.17 `CI_JOB_TOKEN` 默认没有 push 权限，照抄 GitHub 会得 403（2026-11-12）

写 `.gitlab-ci.yml` 时按 GitHub 的习惯写了：

```yaml
- git remote set-url origin "https://gitlab-ci-token:${CI_JOB_TOKEN}@${CI_SERVER_HOST}/${CI_PROJECT_PATH}.git"
```

**这条命令本身没错，错在它默认不生效。** GitLab 官方文档：
「允许使用 CI/CD 作业令牌进行身份认证的 Git 推送请求，**此设置默认关闭**。」

`CI_JOB_TOKEN` 默认只能 clone / pull / 读写 Registry / 下载 artifacts，**唯独不能 push**
（最小权限设计，防止被注入的构建脚本改源码）。所以 push 时得到 403，
**而报错信息里完全没提「是权限开关没开」**，只会让人去怀疑 token 拼错、分支保护、URL 格式。

⚠ 这个错和 7.16 是同一类：**「配置写对了但默认不生效」比「写错了」更难查**，
因为没有任何一处语法有问题，静态检查也查不出来。

**对本项目尤其致命**：深交所份额接口忽略日期参数、只能逐日累积，
**不 push 回仓库 = 那一天的份额永久缺失**。沪市和两融都能回补，只有深市这 6 只不能。

修法（`.gitlab-ci.yml` 已改）：
① 优先用项目访问令牌 `PUSH_TOKEN`（Developer + `write_repository`），没有则退回 `CI_JOB_TOKEN`；
② push 失败时打一段 ✗ 提示，写清去哪个菜单勾什么，而不是甩 403；
③ 顺手补了两个连带问题 ——`update` 加 `allow_failure: true`、artifacts 加 `when: always`。
否则「数据抓到了、只是没推回去」会让依赖它的 `pages` **被直接跳过**，页面反而发不出去。

**教训：迁移 CI 平台时，最该先查的不是语法差异，是「凭据的默认权限」差异。**
GitHub 的 `GITHUB_TOKEN` 默认可写、GitLab 的 `CI_JOB_TOKEN` 默认只读，这一条决定了整条流水线能不能闭环。

### 7.18 用「分位」下结论，却没定死参照系 → 结论正好说反（2026-11-12）

这条不是代码 bug，是**推理 bug**。它比前面 17 条都难发现，因为：
**代码跑得通、数字算得对、页面上也没有任何异常，只是结论是反的。**

原来页面上写「两融余额一年分位 2%（降杠杆）」。数字没错（23,023 亿确实在近一年的 2% 分位），
**但结论反了** —— 用全历史当参照，同一个数是 **86% 分位（偏高）**。

| 参照窗口 | 分位 |
|---|---|
| 全历史（2018 起） | 86.1% |
| 近 5 年 | 77.8% |
| 近 3 年 | 62.9% |
| 近 2 年 | 44.4% |
| **近 1 年** | **2.0%** |

**根因：近一年窗口里只装了一个泡沫峰**（占比 2.90%，2026-07-13）。
拿这一年当基准，「从峰顶退下来」必然显示为「接近最低」。
**「退坡」和「杠杆低」是两件事，不能共用同一个数表达。**

同理，余额的**绝对值**本身也有陷阱：2018-08 流通市值 39.5 万亿 → 现在 91.2 万亿（2.3 倍），
两融 8,734 → 23,023 亿（2.6 倍），**两者同步涨**。所以余额一路创新高，杠杆率其实只从 2.19% 走到 2.49%。
**看余额永远看不出杠杆紧不紧，必须除以流通市值。**

**修法**：拆成两个独立问题，各配各的参照系，并且在页面上**明写参照系是什么**：

| 问题 | 指标 | 参照系 | 当前 |
|---|---|---|---|
| 水位 | 两融 ÷ 流通市值 | 2018 年以来**全历史** | 2.49% → 偏高（86% 分位） |
| 方向 | 近 20 日余额变化 | 只看方向 | −2,328 亿 → 在退 |

⚠ **教训一：凡是用「分位」「百分位」「相对水平」下结论，必须同时说清分母窗口。**
只写「2% 分位」不说窗口，等于没说 —— 同一笔钱在 5 个窗口里能得出 5 个相反结论。

⚠ **教训二：指标名字要能自解释。**「两融余额」回答不了「杠杆高不高」，
因为它是金额不是比率；换成「每 100 元流通股里有多少是借来的」，就不需要任何背景知识。
**如果一个数需要用户先懂一个行业基数才能读，那这个数就该换掉，不是加注解。**

⚠ **教训三：这类错误不会自己冒出来。**前 17 条都有报错、白屏、数字对不上之类的信号，
这一条什么都没有。唯一的发现方式是**用户说「我看不懂」** ——
所以「看不懂」要当成 bug 报告，不是当成需要科普。

### 7.19 只给一个标准 = 没给标准：用户一句「给多个」推翻了第一版（2026-11-12 同日）

修正 7.18 之后，我只给了「融资余额 ÷ 流通市值」**一把尺子**，并在页面上写
「水位偏高 + 正在退」这一句合起来的结论。

用户第二句：**「杠杆的水位标准给多个，不要只有一个。」**

这一句把问题点破在更深一层：**7.18 的错，本质上不是「窗口选错」，
而是「试图用一个标量描述一个多维状态」。** 换窗口只是换了个错法。

#### 为什么一个标准不够（数据证明，不是讲道理）

拆成三个后算秩相关，三者并不重复：

| 组合 | Spearman ρ | 含义 |
|---|---|---|
| ① 水位 vs ② 交易杠杆 | +0.19 | 存量重 ≠ 成交热。仓位可以很重但捂着不动 |
| ① 水位 vs ③ 方向 | **−0.41** | 水位高时往往正在退 —— 这个「反向」本身是信息 |
| ② 交易杠杆 vs ③ 方向 | −0.28 | 同上 |

**如果只看 ①，你会得到「偏高」就停手；三者一起看，才看出「水位偏高 + 热度偏高 + 方向在退」
这个最该警惕的组合。** 一个标准只能给出一个形容词，给不出「矛盾」。

#### 淘汰候选也要记下来

不要只记「选了什么」，要记「为什么没选别的」，否则下次又会想起同一个候选再走一遍：

| 候选 | 淘汰理由 |
|---|---|
| 两融余额 ÷ 流通市值 | ρ=+0.94，与 ① 实质是同一个数（融券只占两融 1.27%） |
| 融券余额 ÷ 流通市值 | 占比 0.032%，无解释力；且融券是看空，语义与「加杠杆」相反 |
| 两融余额绝对值 | 与市值同步增长（2.3 倍 vs 2.6 倍），永远看不出紧不紧 |

⚠ **教训一：判「某个指标够不够」之前，先问「它答的是哪个问题」。**
杠杆至少有三个问题：仓位多重（存量）、交易多依赖借钱（流量）、在加还是在还（方向）。
一个数答不了三个问题，硬答就会像 7.18 那样自相矛盾。

⚠ **教训二：多个标准的门槛是「互不重复」，不是「越多越好」。**
必须有相关性证据（这里是秩相关）支撑「它们不是同义反复」，
否则列五个只是把同一个数说五遍，反而更看不懂。**淘汰的候选要留档。**

⚠ **教训三：矛盾的组合才是信息，不要为了「给一个明确结论」把矛盾压平。**
用户要的是判断，不是形容词。把「偏高 + 偏高 + 在退」压成「杠杆偏高」，
就把最关键的那半句（增量已经停了）丢掉了。

### 7.20 第三把尺子用中位数当分界，把「在加」判成了「在退」（2026-11-12 同日，自查发现）

三把尺子的档位边界本来都用基准期实际分位的 10% / 50% / 90% 切，这在前两把上是对的。
但第三把（20 日净买入 ÷ 余额）的中位数是 **+0.76%** —— 融资盘长期净增，这是常态。

**结果：+0.5%（明显在加）会落进「在退」档，方向直接说反。**

可怕的地方是：代码不报错、数字全对、页面正常，**只有把每档的实际占比算出来才看得见**。

改法：`series_stats(..., mid=0)` —— 第三把的中间分界强制用 0。
- ① ② 是「高度」，没有天然中点 → 用中位数合理；
- ③ 是「加减」，**0 就是「不加也不退」的真实分界**，不能被中位数顶掉。

改后四档分布：

| 尺子 | 改前 | 改后 |
|---|---|---|
| ① 水位 | 10/40/40/10 | 10/40/40/10（不变） |
| ② 交易杠杆 | 10/40/40/10 | 10/40/40/10（不变） |
| ③ 方向 | 10/40/**40**/10（中位 +0.76 当分界） | 10/**32**/**48**/10（0 当分界） |

⚠ **教训：有绝对零点的量，分界必须尊重零点。**
凡是「差值 / 增减 / 净流入」这类指标，0 是有含义的（不加也不退），
拿分位数当分界会把「小幅为正」判成「负」。**这个错不会在数字上暴露，只能在分布上暴露。**

### 7.21 为了「横着能比」统一窗口，代价是「竖着看不见锚」（2026-11-12 同日，用户第三次追问才发现）

上一轮做了一件对的事：三张小图统一从 2019-01-02 起画，让每个横向像素指同一天。
**但统一窗口有个副作用我没算：最早的那段被一起砍掉了，而 2015 年的峰就在那一段里。**

结果是一个很讽刺的局面：
- 图变「严谨」了（三张可比）
- 却失去了回答「现在算不算高」的能力（看不到历史最高）

读者在 2019 年以来的区间里看，最高点 2.90%，当前 2.49% —— **像已经快到天花板**。
放回 12 年，最高 4.70%，当前 2.49% —— **还不到一半**。同一根线，两句相反的话。

⚠ **教训：统一窗口是「可比性」的手段，不是目的。**
当「可比」和「有锚」冲突时，正确做法不是二选一，而是**给两个视图**：
- 多指标对比 → 必须同窗口（否则读者横着比错）
- 单指标定位 → 必须长历史（否则读者不知道自己站在哪）

**别把为 A 做的约束，套到不需要 A 的地方去。** 这一条和 7.19 是同一个毛病的两面：
上一轮是「只给一个标准」，这一轮是「只给一个窗口」。

**还有一条更细的：`min/max` 一改，图里所有「相对点位」的绘制都得重算。**
这轮把 `suggestedMin/Max` 换成硬边界（修好「轴被外扩、上半张空白」），
顺手就把峰谷标注挤出了画布 —— 因为标注的定位规则（峰上/谷下）是按旧的松轴写的。
**改一个约束，要回头检查所有依赖它的地方。**

### 7.22 两块面板被删：**论证比结论长十倍，等于没给结论**（2026-11-12）

评审意见很直接：两块内容「**看不懂**」，点名删掉。

| # | 被删的 | 它本来想说什么 | 为什么该删 |
|---|---|---|---|
| ① | 买卖拆分整块（标题：「规模 +287%，但净流入只有 +1460 亿 —— 剩下的不是新钱」） | 规模涨 287% 不等于赚了 287%，差额是存量浮盈 | **数据全对**（净流入 1459.7 + 浮盈 2479.7 = 规模增加 3939.4），但为了证明「不是算错」，摆了 3 张 KPI + 4 段长解释 + 2 张表 + 逐只价差表 |
| ② | 平准周期（标题：「一轮完整的平准周期：11 段」） | 份额 × 价格两维，能读出「逆势承接 / 获利了结」 | 11 阶段 × 7 标的 = **77 格数据**，读者记不住任何一格；且**切分点是人选的**，换个人会切出另一套 11 段 |

**① 的教训最值得记：我把「证明自己没错」当成了「交付结论」。**

每一层都对，但**它是写给「怀疑者在审查」的，不是写给「用户想看今天怎么样」的**。
一个人每天打开这个页面，想知道的是「今天钱进了还是出了、杠杆高不高」，不是「这个恒等式为什么成立」。

> **判据：页面上的每一块，问一句「他明天打开会看这一块吗」。不会看的，就是不该放。**
> 自证材料可以进 README、进代码注释，但不该占正文。

**② 的教训是另一种：数据量 ≠ 信息量。**

77 格里有信息量的其实只有一句：**份额涨 + 价格跌 = 逆势承接**（这条判读规则本身就是全部价值）。
把它做成 11 张表，等于把一句结论稀释进 77 个数字里 —— **稀释不是严谨，是让读者放弃**。

- 删除原因写进 HTML 注释，避免下一轮又「想起来觉得挺好」再加回去

### 7.23 给小米 Android 补 PWA：4 处元件缺失 + 1 处 CI 漏发（2026-11-12）

触发点：**使用设备是小米 Android，不是 iPhone** —— 原来那条「iPhone Safari → 添加到主屏幕」走不通。

查下去发现更彻底的：**这个页面压根没有任何 PWA 元件，在任何浏览器里都不会弹安装。**

**四处缺失（head 里一条都没有）**：

| 元件 | 原状 | 后果 |
|---|---|---|
| `manifest.json` | 不存在 | Chrome 不知道这是什么应用 |
| `<link rel="manifest">` | 不存在 | 同上 |
| 192 / 512 PNG 图标 | 不存在 | WebAPK 无法生成 |
| `theme-color` / `background_color` | 不存在 | 启动白屏闪一下，状态栏和页面不同色 |

**第五处、也是真正会让人查半天的**：

```yaml
# 原来
cp demo_site.html public/index.html
cp -r data public/data
# → manifest.json 和 icons/ 根本没进 public/
```

**本地双击打开一切正常（相对路径都在），一上线就 404，Chrome 静默失败。**
这种错最费时：没有错误信息，只有「按钮不出现」。

**教训（可以推广到所有静态站的 CI）**：

> **页面引用了什么文件，CI 产物就必须包含什么文件。**
> 别靠「我本地打能开」验收 —— 本地是文件系统，线上是 CI 拼出来的目录，两者不是一回事。
> 所以这次在 CI 里加了 `test -f` 自检：**缺文件就让 job 报错，别让它静默发一个残站**。

**顺带修掉的 390px 老问题**：4 张 KPI 排成 3+1（见六之补 ⑧）。
`auto-fit(minmax(118px,1fr))` 在 370px 可用宽度里刚好塞 3 列 —— 和第 7.20 的「6 列装 7 张」同源，
**一组卡必须整行**，这条已经犯过两次了。

#### ⚠ 补充：第一次真跑 CI 之后，又炸出三处（2026-11-12 下午）

上面 7.23 说的是「元件缺了」。**真跑起来之后，问题换了一种形态：元件都在，但每天被悄悄拆掉。**

**㉔ 抓取全失败时把 227 KB 的有效数据覆盖成 0 KB**

第二次 CI（run 43182246241）东财全站掐断，10 只标的全部 `RemoteDisconnected`：

```
▶ fetch_price_bfq.py
写入 data/prices_bfq.json  (0 KB)  成功 0/10
▶ compute_demo.py
  组合单日净流入 +0.00 亿 ｜ 近5日 +0.0 亿 ｜ 近20日 +0.0 亿
```

根因就一行：`json.dump(out, open(fp,'w'), ...)` —— **`out` 是空的时候照样写。**

> **比崩溃更糟的是静默写空。**
> 崩溃至少看得见；写空之后日志里只有一行「0 KB」，页面长得跟正常一样，只是所有数字变成 0。
> 而且上一轮我加的「判空兜底」正是为了不让 compute_demo 崩 —— 结果把**崩溃换成了静默写空**，
> 等于把火警拆了却没修火。**兜底不能只兜「不报错」，还要兜「不出错结果」。**

改成三条规矩：

| 场景 | 行为 | 退出码 |
|---|---|---|
| 全失败（0 只） | **一个字都不写**，旧文件原样保留 | 2 |
| 部分成功（如 3/10） | **合并**进旧数据，没抓到的沿用旧值 | 1（报警）|
| 全成功 | 全量写盘 | 0 |

**为什么「部分成功」也必须合并、不能整体替换**：某只标的瞬时故障，如果整体替换，
它那一段历史就被清空了，净流入从该日起全变 0 —— 又是一次静默。

写盘一律走 `.tmp` + `os.replace`（原子），不留半截文件。

`fetch_inst.py` 有同一处风险，同样处理；**顺带发现它 `main()` 没有 `sys.exit`，
退出码恒为 0，失败永远传不到报警里。**

**㉕ CI 每天把离线版换成 CDN 版，还伪装成「更新数据」**

`update.py` 第 6 步写的是 `run('build_demo.py')`，**没有 `--offline`**。
而 `build_demo.py` 默认走 CDN（1,762 KB），只有 `--offline` 才内联 Chart.js（1,967 KB）。

于是每天 CI 跑完：

```
用 1,762 KB 的 CDN 版覆盖仓库里的 1,967 KB 离线版
→ 以 "data: 更新至 2026-11-11" 的名义 commit 回来
```

**提交信息看起来只是更新数据，实际每天把「加到手机桌面后断网也能看」拆掉一次。**
我是拿 `git show origin/main:demo_site.html | grep -c cdnjs` 返回 1 才确认的 ——
光看 commit message 和页面外观，完全看不出来。

修法：`update.py` 加 `--offline`；**两个 CI 文件都加断言**，是 CDN 版就 `exit 1`。
修完 CI 日志里出现 `✓ demo_site.html 为离线版（Chart.js 已内联）`。

> **推广：凡「本地构建出来的是 A 版，CI 构建出来的是 B 版」，就是一个隐形回归。**
> 判据不是「CI 绿了」，是**把 CI 的产物和本地的产物做二进制比对**。
> 这次两边都是 1,967,677 B，只差 28 个字符（`updated_at` 时间戳），肉眼看页面一模一样。

**㉖ 价格混进了当日未收盘的半日价**

同一次 CI 输出：

```
510050  1906 根  2019-01-02 → 2026-11-12  末价 2.884
2026-11-12 上交所无数据（非交易日或未发布）
```

**价格到了 11-12，份额只到 11-11。** 而净流入 = 份额差 × 当日真实价 ——
拿半天的价格去乘，比不更新更糟。

`fetch_index.py` 早就剔除了当日（它注释里记着「10:21 抓到 8,486 亿半日量」这个坑），
**`fetch_price_bfq.py` 当时没跟上**。同一个项目里，一条规则只在一半的抓取器上生效。

修法：`fetch()` 统一 `只接受日期 < 今天`。同时清掉线上已混入的 6 只标的的 11-12 行并重算。

> **推广：一条数据纪律写进了注释，不等于写进了代码。**
> 判断方法是**列出所有抓取器，逐个问「这条规则你遵守了吗」**，而不是「我记得我处理过」。

**这一轮之后的 CI 实测（run 43184092274，success）**

这次东财又全挂了（0/10），正好撞上刚修的那条路径：

```
✗ 一只都没抓到，不写盘。旧文件保留 6 只 / 10148 根 (227 KB)
✓ demo_site.html 为离线版（Chart.js 已内联）
```

**同样的故障，这次一分钱没丢。** 线上实测：

| 路径 | 状态 |
|---|---|
| `/` | 200 · 1,967,677 B（= 离线版，CDN 引用 0 处）|
| `/manifest.json` | 200 · 817 B |
| `/icons/icon-192.png` | 200 · 5,301 B |
| `/data/prices_bfq.json` | 200 · 232,355 B（不再是 2 B 空文件）|

**㉗ 前复权价 `prices.json` 根本不在日常更新链里，永久停更**

这是五处里**最隐蔽的一处**：它连「失败」都不会发生。

```
$ grep fetch_history scripts/update.py
（空）
```

`prices.json`（前复权，页面画价格曲线用的那个）只有一次性回补脚本 `fetch_history.py` 会写，
而那个脚本的判据是**「起点够早就跳过」**：

```python
if have and have[0][0] <= need:
    print(f'  {code} 已有 {len(have)} 根，覆盖充分，跳过')
    continue
```

于是**回补一次成功之后，它永远不会再更新**。价格曲线会一天天变旧，
而页面上没有任何东西会变红 —— 因为**它压根没被抓取，所以连一条失败记录都不会产生**。

> **推广：这一类故障没有失败日志可查，只能靠「数据到哪天」自己去看。**
> 前四处还能从退出码、日志、文件大小里发现；这一处只能问一句
> **「这个文件是谁在写、多久没写了」**。

修法：加 `--refresh-prices` 跳过「起点判断」无条件全量重抓，并接进 `update.py`。

**为什么必须全量而不是增量**：前复权序列一旦某只标的**分红**，历史值会整体重算。
增量续接会和已有历史对不上（同一天两个价），只能整段覆盖。
9 只 × 1900 根实测十几秒，这个代价完全可接受。

**㉘ 然后我给上面五处开了一副药：常驻的数据体检栏**

五处故障的共同病根**不是「没写 if」，而是「坏了不吭声」**。
所以修法不是再补五个 `if`（下一个故障还是会长在别处），
而是**给整个抓取层装一个常驻仪表盘，让「没抓到」这件事在页面上没法藏**。

用户当时的原话是：

> `第三条吧，但他得告诉我停了，当日没有获取到`

三层结构：

```
抓取层  scripts/_fh.py  report()   →  data/fetch_status.json（保留 14 天）
计算层  compute_demo.py            →  demo.json 的 health 字段
展示层  demo.html                  →  常驻体检栏，坏项默认展开
```

**★ 状态判定必须是两维的，只看一个会误判**

| 维度 | 字段 | 规则 |
|---|---|---|
| 新鲜度 | `lag` = 今天 − 数据最后一天 | 超过 `LAG_OK` → `stale`（停更）|
| 完整性 | `got / want` | 少于 `want` → `partial`（部分缺）|

实测踩到的例子：`价格（不复权）` 日期是 **2026-11-11**（lag = 0，看着完美），
但**只覆盖 6/10 只** —— 只看日期会判成「正常」，而实际净流入只算了 60% 的标的。
**「日期新」不等于「数据齐」。**

`LAG_OK` 按数据源各自给，不能用一套标准：

```python
LAG_OK = {
    'shares':   1,   # 上交所 T 日晚发布，T+1 可见
    'price_bfq': 0,  # 收盘后即可得
    'price_qfq': 0,
    'index':    0,
    'margin':   1,   # 两融 T+1 晚间公布
    'dividend': 0,
    'inst':     180, # 半年报/年报，滞后两个月
}
```

**机构持仓如果也给 1 天，会天天报「停更」** —— 一年只发 2 次，滞后两个月是常态。
一份天天误报的仪表盘，等于没有仪表盘。

**★ 三种状态必须一眼可分**

`ok`（绿）/ `partial`（琥珀）/ `stale`（琥珀 + ⏱）/ `fail`（红）。
全用同一个颜色，人就会习惯性忽略它 —— **那就等于又回到了静默。**

**★ 首次部署时 `fetch_status.json` 不存在，不能显示「未生成」**

只有抓取脚本跑过才有这个文件；只跑 `compute_demo.py`、或者刚 clone 下来时它是空的。
所以我加了 `_derive_health()`：**没有上报记录时，直接从数据文件反推一份**。

反推一律标 `ok` / `stale`，**绝不编造 `fail`** ——
文件在、日期新，确实说明数据可用；至于「这次有没有抓、抓了几只」，没记录就是不知道，不能猜。

> **把「我没记录」说成「数据有问题」，和把「数据有问题」说成「一切正常」，
> 是同一种病：拿不确定的东西冒充确定。**

反推时踩到一个坑：`last_of(sorted(shares))` 对 `dict` 迭代出来的是**字符串**，
`x[0]` 会取到第一个字符 —— `'2026-11-11'` → `'2'`。拆出 `last_key()` 才修掉。

**★ 上报必须 best-effort**

磁盘满、JSON 损坏都不能把**本来成功的抓取**拖成失败。所有异常吞掉，只打一行：

```
  ⚠ 状态上报失败（不影响本次抓取）：OSError: ...
```

**★ 手机端只展开坏项**

7 行全铺开实测 **570px**，把首屏整个推走 —— 那是「报出来了但挡着正事」，和没报一样糟。
改成窄屏只展开坏项 + 一行「其余 N 项正常（点开看全部）」。

**实测（首轮，只有 1 项坏）**：1440px → 255px，390px → 172px。

**★ 14 天历史，不是只留最后一次**

只留最后一次，就看不出**「连续三天没抓到」**和**「今天偶尔没抓到」**的区别 ——
这两件事判断完全不同。所以加 `days_bad` 字段，跨天累积，14 天滚动清理。

**实测：全失败时上报真的落盘**

```
✗ 一只都没抓到，不写盘。旧文件保留 6 只 / 10148 根 (227 KB)
退出码 2
{"price_bfq":[{"at":"2026-11-12 17:23","state":"fail","got":0,"want":10,
               "last":"2026-11-11","note":"今日 0/10 只，沿用旧价"...}]}
```

注意 `last: "2026-11-11"` 是**从旧文件读出来的**（不是 `null`）——
这样页面才能算出「落后 1 天」。报「停在 11-11」比报「没有日期」有用得多。

**㉙ 然后体检栏自己炸了四处 —— 全是「它自己会骗人」**

装好之后再跑一遍真实流程，发现的问题比它要修的那五处更值得记：
**一个错误设计的体检栏，比没有体检栏更糟 —— 它让人以为查过了。**

前两处是逻辑错（会给出错结论），后两处是呈现错（正确结论看不出来）。

**第一处：`price_qfq` 十只全失败，却上报「ok 10/10 正常」**

同一次运行里，日志写着 10 行「失败」，体检栏写着「全部正常」。错在：

```python
_got = len([k for k, v in prices.items() if v])   # ← prices 已把旧文件读进来了
```

`prices` 是「先把旧文件读进来、失败就保留旧值」的字典，所以**就算 10 只全失败，
字典里仍有 10 项**。判据必须是「本次抓取的结果」，不是「合并后字典的长度」。

> **这条我在 `fetch_price_bfq.py` 里专门写过注释防它，隔了几百行又犯了一遍。**
> 说明「知道」和「做到」之间隔的不是理解，是**检查项** ——
> 现在两边都改成用 `ok_codes` / `bad_codes` 两个显式列表，不再从结果字典倒推。

**第二处：`summarize(today=days[-1])` —— 拿被测对象当尺子**

`days[-1]` 是**数据自己的最新日期**。今天 11-12、数据停在 11-11 → `lag = 0`，显示「当日，正常」。
**就算数据停在 11-05，基准也跟着变成 11-05 → `lag` 还是 0。**

也就是说这一栏的 `stale` 分支**永远不可能触发** —— 它装饰得很像体检，实际什么也没查。
我写的时候注释还是「数据和页面必须同源，否则跨零点会差一天」，想得挺周到，方向是反的。

改成 `date.today()`。跨零点差一天是真的，但那是 1 天的事；拿错基准是「永远为 0」的事。

**第三处：`compute_demo.py` 排在 `fetch_dividend` / `fetch_history` 前面**

`update.py` 里它的位置是第 5，而那两个是第 6、7。
于是**后两项的体检结果永远进不了当天页面**，要等第二天才显示前一天的状态。

实测证据：`data/fetch_status.json` 里有 **6 项**，`demo.json` 的 `health` 只有 **4 项**。
页面上少了两项，而且不会报错 —— **顺序错了，等于给体检栏开了个后门。**

改成：所有抓取在前，`compute_demo` 收尾。

**第四处：判 stale 用错了表 —— 周末和春节会天天红**

原来是「`lag > LAG_OK` 就算停更」。但 `LAG_OK` 的语义是**「这个源天生滞后几天」**
（两融 T+1、上交所 T+1），不是**「多久没新数据才算停了」**。

数据停在 T-1 是完全正常的，拿它判 stale，每个交易日都会误报。
**一份天天误报的仪表盘会被当成噪音关掉**，那就又回到静默。

拆成三个独立判据，各查各的：

| 判据 | 查什么 | 阈值 |
|---|---|---|
| `state` 本身 | 抓取当场成没成 | fail / partial 照实显示 |
| `days_silent` | **这一项多久没被上报过** | > 2 天 → stale |
| `lag` | 数据本身停了多久 | > 10 天（`SRC_STALE_DAYS`）→ stale |

`days_silent` 是这次新增的，也是**唯一能抓到 ⑤ 号 bug 的判据**：
`prices.json` 那种「脚本根本没被调用」的停更，不报错、不产生失败记录，
只能从「这项多久没被上报过」看出来。

10 天这个数不是拍的：A 股最长休市是春节（约 9 天）。

**实测六个场景（全部判断正确）**

| 场景 | 数据到 | 脚本上报 | 判定 |
|---|---|---|---|
| 两融 T+1 | 昨天 | 今天 ok | ✅ ok（不能报 stale）|
| 长假中 | 7 天前 | 今天 ok +「今日无新数据」 | ✅ ok（不能报 stale）|
| 源站真停了 | 42 天前 | 今天 ok | 🕒 stale「源站已 42 天无新数据」|
| 部分缺 | 昨天 | 今天 partial 4/10 | ⚠ partial |
| 全失败 | 7 天前 | 今天 fail 0/11 | ❌ fail |
| **脚本没跑** | 8 天前 | **8 天前** ok | 🕒 stale「已 8 天没有抓取记录」|

最后一行就是原来永远抓不到的那一类。

**第五处（呈现）：把堆栈直接贴上屏，手机上吃掉 44% 首屏**

`_fh.py` 文件头我自己写着「`note` 直接上屏，要写人话不是写堆栈」，
然后在 `fetch_index.py` 里写：

```python
note=f'{type(e).__name__}: {e}'
# → RemoteDisconnected: Remote end closed connection without response
```

手机上它折成 3 行、单行 **109px**，整栏被这一条撑到 **373px**，
而首屏只有 844px —— **报了，但把正事挡掉了。**
加了 `_why()` 翻译成「接口主动断连（境外 IP 常见）」，技术细节留在 print 日志里。

**第六处（呈现）：窄屏下「×」图标被挤到单独一行**

`.fh-nm{flex:1 1 100%}` 让名字独占整行，flex 换行时把 `.fh-ico` 留在上一行 ——
截图里就是一个「×」孤零零悬在标题上方，像漏渲染。

改成 `flex:1 1 calc(100% - 21px)`（图标 13px + gap 8px）。
**顺带把高度从 335px 降到 261px** —— 图标回到同一行，每行少一行高度。

**本轮最终实测（6 项体检，3 项坏）**

| 宽度 | 体检栏高度 | 横向溢出 |
|---|---|---|
| 1440 | 225px | 无 |
| 900 | 225px | 无 |
| 640 | 241px | 无 |
| 430 | 261px | 无 |
| 390 | 261px | 无 |
| 360 | 261px | 无 |

所有 `note` 的 `clipped` 全为 `false`。首屏（390×844）占比 31%。
桌面 6 行全铺开，手机 3 坏项 + 1 行「其余 3 项正常」。

> **这一轮真正学到的：**
> 给系统装仪表盘的时候，**仪表盘本身必须先被体检一遍**。
> 五处故障里有三处是「数据对不对」，这一轮四处里有三处是「体检说得对不对」——
> 后者更难发现，因为它的输出长得跟正确答案一模一样。
> 判据只有一条：**故意把数据弄坏，看它红不红。** 红不了的那一栏，就是装饰品。

**㉚ 第一次真跑 CI：体检栏报对了，但暴露了一个设计错误**

上线后手动触发 CI（run `43198402437`，22 分钟，success），日志出来是这样：

```
✗ 一只都没抓到，不写盘。旧文件保留 ...        ← 前复权价：0/10
写入 data/prices_bfq.json (339 KB) 抓到 8/10   ← 不复权价：8/10
  数据体检：6 项，3 项有问题
    · 上证指数 / 两市成交额：落后 1 天  接口主动断连（境外 IP 常见）
    · 价格（前复权，画曲线用）：落后 1 天  本次 0/10 只，沿用旧价
    · 价格（不复权，算净流入用）：落后 1 天  2 只未获取，159545 159919 沿用旧价
```

体检栏本身**完全正确** —— 三种状态都对：
`fail 0/10`、`partial 8/10`、`ok 7/7`，页面上红、琥珀、绿三色分得干净。
（线上实测：1440px 225px、390px 281px，六宽度无溢出，`clipped` 全 false。）

**但它暴露出我上午那个修法是错的。**

同一批标的、**同一个 `push2his` 接口、同样参数**，`fetch_price_bfq` 拿到 8/10，
`fetch_history` 拿到 **0/10**。不是接口有问题，是我两个脚本写得不一样：

| 脚本 | 重试次数 | 退避 |
|---|---|---|
| `fetch_price_bfq.py` | 4 次 | 0.8 / 2 / 4 秒 |
| `fetch_history.py` | **3 次** | 1 / 2 秒 |

东财对境外 IP 是**间歇性**掐断（实测同一请求前后差不到 1 秒就一通一断），
所以「多试一次」直接决定成败。3 次约 70%、5 次约 90% —— 这就是 8/10 和 0/10 的全部原因。

> **「接口挂了」这个判断，有三分之一的时候其实是「我试得太少」。**
> 而这类误判有个很坏的副作用：它会让人去换源、加代理、写更复杂的重试框架，
> 唯独不会去数一数「另一个脚本试了几次」。

**更要命的是这个组合：**

上午我为了让 `prices.json` 不再停更，让它**每天无条件全量重抓** 10 只 × 1900 根。
逻辑上没错（前复权一旦分红，历史值整体重算，增量接不上），但它把
**「偶发失败」变成了「每天一次风险」** —— 每天赌 10 次全量请求都不被掐断，
赌输的那天价格曲线就停一天。

**改成「增量 + 重叠校验」，判据从「时间到了」换成「数据自己说」：**

```
日常：只抓最近 40 天（响应体从 1900 根降到 ~30 根）
      ↓
拿这 40 天和旧数据【重叠区逐日比对】
      ↓
对得上   → 没除权，把新日期接上去（增量，够了）
对不上   → 发生过除权，历史必须整段重算 → 自动转全量
```

为什么这个判据成立：前复权序列一旦某只分红，**同一天会出现两个价**。
所以「重叠区是否吻合」正是除权的直接指纹 —— 不用猜哪天分红，让数据自己说。

**为什么敢这么改**：写了 `tests/test_price_incremental.py`，六个场景离线跑，
不联网、不依赖真实接口：

| 场景 | 期望 | 结果 |
|---|---|---|
| 重叠完全吻合 | 走增量，不重抓历史 | ✅ 100 根 + 5 根 = 105 根 |
| 重叠数值不一致（模拟除权） | 必须全量重抓 | ✅ 10 只全部重抓 |
| 近端抓取失败 | 旧数据原样保留 | ✅ 仍是 100 根，分毫未动 |
| 近端返回空（接口改版） | 旧数据原样保留 | ✅ 未动 |
| 没有旧数据 | 全量回补 | ✅ |
| 旧数据起点太晚 | 全量回补 | ✅ |

14 项断言全过。**这段逻辑决定「价格曲线会不会停更」，而停更是这个项目最隐蔽的故障
（不报错、不产生失败记录），所以它必须有不依赖网络的测试钉着。**

三个打东财的脚本重试次数也统一到 5 次、退避 1/2/4/8 秒。

## 十一之三、当日异动度：基线怎么定（2026-11-12）

用户要求：**「首页当日净流入增加一个百分比，基数是日常近一段时间的普遍流入水准，目的是监控当日是否有异动。」**

这里最容易犯的错是「拍一个数字当基线」。所以先用真实分布把窗口和阈值都算出来。

### ① 为什么不能用固定基线

```
全历史 |flow| 中位数      15.7 亿
近 250 日 |flow| 中位数   34.9 亿
近 60 日  |flow| 中位数   23.8 亿
近 20 日  |flow| 中位数   56.9 亿
```

**同一只组合，不同阶段的「常态」差 3.6 倍。** 拿 15.7 亿当基线，2026 年 11 月每天都会显示
「3–30 倍异动」—— 天天报警等于没报警。

### ② 为什么用中位数，不用均值

净流入分布是**重尾的**：单日 ±450 亿能把 60 日均值拉高两三成，基线自己被异常值污染，
下次真异动就测不出来。中位数对极端值免疫 —— 60 天里就算有 10 天是 300 亿，中位数仍在常态水平。

### ③ 为什么用 `|flow|` 的绝对值

要测的是「幅度不寻常」，不是「方向」。−300 亿和 +300 亿都该报。
若用带符号的中位数，正负互相抵消，全历史带符号中位数只有 **−0.1 亿**，除以它直接爆表。

### ④ 窗口长度：三种窗口的实测稳定性

| 窗口 | `|倍数|` 各年 >3 的占比跨度 | 问题 |
|---|---|---|
| **60 日** | 6.6% ~ 17.6%（**11pp**） | ✅ 采用 |
| 120 日 | 7.0% ~ 21.0%（14pp） | 略僵 |
| 250 日 | 5.8% ~ 31.2%（**25pp**） | 2026 年 31% 的交易日都被判「>3 倍」，失去区分度 |

250 日的问题很具体：它会用 2025 年的低水位去衡量 2026 年的高水位。60 日能跟上状态切换。

### ⑤ 阈值：用「年度触发次数」反推，不是拍脑袋

```
门槛   2020  2021  2022  2023  2024  2025  2026    含义
2.0×    58    62    52    49    59    52    66     每周都报 → 等于没报
4.0×    17    10    10    16    25     5    27     年均 16 次，每月 1.3 次  ← 异动线
8.0×    11     1     1     7    15     2    18     年均 3 次，一年几次      ← 极端线
```

分档后的全样本占比：**安静 48.9% / 常态 27.0% / 偏高 17.5% / 异动 4.6% / 极端 2.1%**

### ⑥ 三条实现纪律

1. **排除当日**：基线只用 `i` 之前的 60 天。含当日的话，超大单日会把基线自己抬起来，倍数被系统性压低。
2. **前 10 天返回 `None`**：样本不足时任何「常态」都是瞎猜，不硬算。
3. **倍数 + 分位互为交叉验证**：倍数看「相对近期常态」，分位看「在一年里的绝对排名」。两个都说异常才可信。

### ⑦ 实测输出（2026-11-12）

```
2026-11-10  净流入 −22.6 亿  ÷ 60日基线 25.0 亿 = 0.90×  [安静]  近一年分位 37%
2026-11-03  净流入 +467.2 亿 ÷ 60日基线 36.6 亿 = 12.75× [极端]  近一年分位 99%
```

同一个数（467 亿）在 11-03 被标成「极端」，在 11-10 的 −22.6 亿被标成「安静」——
这正是要的效果：**读数不再是孤立的数字，而是自带参照系。**

## 十一之四、量能与杠杆：为什么这两个分母比资金流本身更值得看

新增 `fetch_index.py` 的成交额 + `fetch_margin.py` 的两融。理由是**同样的 120 亿，在不同水位里含义完全不同**：

- 在 8,000 亿的地量里是「有人在硬扛」
- 在 2.6 万亿的天量里只是正常换手

### 关键发现（2026-11-12 首跑）

```
ETF 近 20 日净流入        +2,299 亿
两市成交额一年分位          12%      ← 缩量
两融余额一年分位             2%      ← ⚠ 这个口径是错的，见 11.4.1
两融 20 日变化           −2,328 亿
两融自 2026-06-25 高点     −7,307 亿（−24.1%，30,330 → 23,023）
```

**两融退出的 2,328 亿 ≈ ETF 流入的 2,299 亿，两个数几乎完美对冲。**
所以「融资盘撤出、转进 ETF」不是猜测，是能对账的。

这直接改写了第九节的结论：10 月那波回流**不是增量资金进场**，
更像是同一批钱换了载体 —— 从带杠杆的个股仓位，换成不带杠杆的宽基 ETF。

### 11.4.1 ⚠ 我原来把「杠杆高低」算错了（2026-11-12 当天修正）

用户原话：**「两融余额是为了判断当前的杠杆率是否足够高，也就是说国家队决定入场了之后，
当前的社会资金和增量资金是否有入场。有没有更简单直接的，可以看出来两融余额当前的杠杆率
处于哪个位置？因为我并不了解日常的两融余额数量，所以这一个简单的数量我并不能理解
当前的杠杆率处于什么状态。」**

这一问直接戳破了原来的口径。**原来页面上写「两融余额一年分位 2%（降杠杆）」——这句是错的。**

#### 错在哪：分位没有定死参照系

同一个 23,023 亿，换窗口得出完全相反的结论：

| 参照窗口 | 余额分位 | 读起来 |
|---|---|---|
| 全历史（2018 起，2000 天） | **86.1%** | 很高 |
| 近 5 年 | 77.8% | 偏高 |
| 近 3 年 | 62.9% | 中等 |
| 近 2 年 | 44.4% | 中等偏下 |
| **近 1 年** | **2.0%** | **极低** |

**两个都对，结论相反。** 近一年窗口里只有一个泡沫峰（占比 2.90%，2026-07-13），
拿这一年当基准，2.49% 当然显示 2%。但这不是「杠杆低」，是**从峰值退下来**。
把「退坡」写成「降杠杆」，是拿一个没定义的相对数当绝对值用。

#### 正确的问法：拆成三个独立问题（★ 三次迭代才定下来）

用户第二句原话：**「杠杆的水位标准给多个，不要只有一个」**。

第一次我只给了「占流通市值」一个。这是不够的 —— 它只回答「仓位有多重」，
回答不了「市场有多依赖借钱交易」和「这个月是在加还是在还」。而这三件事可以互相矛盾，
**矛盾本身就是信息**（现在正是：水位偏高、热度偏高、方向却在退）。

| # | 标准 | 公式 | 通俗读法 | 当前值 | 分位 | 档位 | 样本 |
|---|---|---|---|---|---|---|---|
| ① | **杠杆水位** | 融资余额 ÷ 流通市值 | 每 100 元流通股里，有多少钱是借来买的 | **2.49%** | 79.6% | **偏高** | 3125 天（2014 起） |
| ② | **交易杠杆** | 融资买入额 ÷ 两市成交额 | 每 100 元成交里，有多少是借钱在买 | **9.03%** | 64.6% | **偏高** | 1905 天（2019 起） |
| ③ | **杠杆方向** | 20 日融资净买入 ÷ 两融余额 | 这一个月，杠杆资金净增/净减了余额的百分之几 | **−10.09%** | 3.7% | **大幅在退** | 3125 天（2014 起） |

**为什么是这三个而不是别的 —— 用秩相关验证过它们不重复：**

| 组合 | Spearman ρ | 判断 |
|---|---|---|
| ① vs ② | **+0.19** | 几乎无关 → 存量重不代表成交热，保留 |
| ① vs ③ | **−0.41** | 弱负相关 → 水位高时往往正在退，这正是要抓的矛盾，保留 |
| ② vs ③ | **−0.28** | 弱负相关，同上，保留 |

**被淘汰的候选（也记下来，免得以后又想起来）：**

| 候选 | 淘汰理由 |
|---|---|
| 两融余额 ÷ 流通市值 | 与 ① 的 ρ=**+0.94**，实质是同一个数。原因：融券只占两融的 1.27%，两者几乎相等 |
| 融券余额 ÷ 流通市值 | 占比仅 0.032%，没有任何解释力；且融券是看空，不是加杠杆 |
| 两融余额绝对值 | 只涨不跌是通胀+市值增长的结果。2018-08 流通市值 39.5 万亿→现在 91.2 万亿（2.3 倍），两融 8,734→23,023 亿（2.6 倍），**同步涨**，看余额永远看不出杠杆紧不紧 |

#### 基准期必须写死 2014-01-01，而且写进数据里

**2010–2013 不能当基准**：那是两融业务刚开、余额从 0 爬坡的阶段（占比 0.07%→1.75%），
那不是「低杠杆时期」，是「业务还没长起来」。把它算进去会把正常水平全抬高。

| 基准期起点 | 样本 | ① 当前分位 | P50 | P90 |
|---|---|---|---|---|
| 2010-03-31 | 4035 天 | 84.2% | 2.20 | 2.64 |
| **2014-01-01（采用）** | **3125 天** | **79.6%** | **2.28** | **2.76** |
| 2019-01-02 | 1905 天 | 85.4% | 2.28 | 2.56 |
| 2021-01-01 | 1418 天 | 80.4% | 2.31 | 2.60 |
| 2024-01-01 | 691 天 | 60.3% | 2.38 | 2.66 |

⚠ **分位在 `compute_demo.py` 里算好、写进 `data/demo.json`，前端只读不重算。**
前端算就必须自己挑窗口，而「挑窗口」本身就是上一版出错的原因。

#### 四档边界也用实际分位切，不拍脑袋

```
① 杠杆水位   很低 < 2.061 ｜ 偏低 < 2.279 ｜ 偏高 < 2.761 ｜ 很高 ≥ 2.761
② 交易杠杆   很低 < 6.75   ｜ 偏低 < 8.47   ｜ 偏高 < 10.37  ｜ 很高 ≥ 10.37
③ 杠杆方向   大幅在退 < −5.14 ｜ 在退 < 0 ｜ 在加 < 9.31 ｜ 大幅在加 ≥ 9.31
```

① ② 用的是基准期内实际分位的 10% / 50% / 90%。实测四档分布都是 **10% / 40% / 40% / 10%**，
说明切点位置合理。

⚠ **③ 的中间分界必须是 0，不能用中位数。** 这是本轮抓到的第二个错：
③ 的中位数是 **+0.76%**（融资盘长期净增，这是常态）。拿它当分界，
**+0.5%（明显在加）会被判成「在退」，方向直接说反** —— 而这个错在数字上完全看不出来。
① ② 是「高度」，没有天然中点，用中位数合理；③ 是「加减」，0 就是「不加也不退」的真实分界。
改后分布变成 10% / 32% / 48% / 10%，符合「长期偏加、极端才叫大幅」的实际情况。

#### 为什么「占流通市值」这个分母是对的

它有一个很直观的解释，不需要懂两融基数：

> **每 100 元流通股票里，有多少钱是借来买的。**

| 日期 | 占比 | 读作 |
|---|---|---|
| 2019-02-25（历史最低） | 1.80% | 每 100 元里有 1.8 元是借的 |
| 2024-09-13 | 2.25% | 救市前夜 |
| 2026-06-25（余额峰） | 2.81% | 泡沫期 |
| 2026-07-13（占比峰） | **2.90%** | 历史最高 |
| **2026-11-11（当前）** | **2.49%** | 高位回落，仍高于中位 |

当前 2.49% → **偏高**（79.6% 分位）。**和原来那句「降杠杆到极低」正好相反。**

#### 结论要改口

| | 原来（错） | 现在（对） |
|---|---|---|
| 水位 | 「一年分位 2%，杠杆极低」 | **偏高**（每 100 元借 2.49 元，79.6% 分位） |
| 热度 | 没有这个概念 | **偏高**（每 100 元成交借 9.03 元，64.6% 分位） |
| 方向 | 「降杠杆」 | **大幅在退**（20 日 −2,328 亿，−10.09%） |
| 合起来的读法 | 增量资金没来 | **水位偏高 + 热度偏高 + 正在退 = 最该警惕的组合** |

三者不矛盾：**杠杆率仍处在历史高位，但融资盘正在撤。**
这和「杠杆已经很低、跌不动了」是完全不同的判断 —— 后者会让人以为下跌空间有限。

**这个组合本身就有含义：不是没人借钱了，是借了还没还完。**
如果是健康去杠杆，应该看到水位同步下移；现在的形态是水位还挂在高位、增量已经停了。

#### 页面上的呈现（改了什么）

| 位置 | 原来 | 现在 |
|---|---|---|
| 首页 KPI | 一行 5 张，「两融余额 23,023 亿 · 一年分位 2%」 | **两行**：第一行 4 张资金流（今天/5日/20日/成交额），第二行 3 张杠杆（水位/交易杠杆/方向）。分两行是因为 7 张挤一行会排成 6+1，最后一张孤零零，读不出「这 7 个数是一组」 |
| 量能面板 | 「两融余额 / 当日融资净买入」两张卡 | 三张图（下条），不再重复放卡 |
| 新增图表 | 无 | **三张小图并排**（`cLev_stock` / `cLev_trade` / `cLev_flow`）：各自独立的纵轴 + 四段色带 + 当前值虚线与右端标签 + 档位边界细虚线 |
| 背离提示 | 用 `pctile<=30` 判「杠杆在退」 | 改读 **`LV.flow.v<0`**（后端算好的方向尺子），不再前端自己拿 `chg_20d` 除一遍 |

**为什么是三张小图而不是一张三条线：** 三者量纲不同（2.49% / 9.03% / −10.09%），
挤进一根轴要么各自归一化（那就看不出绝对值了），要么互相压扁。
而这三张图的价值恰恰是「各自落在自己那套标准的什么位置」。

**但横轴必须共用同一个时间窗**（`levers.win = 2019-01-02`，取三者里最晚的起点）：
否则读者会拿左图 2015 的峰去对齐右图 2019 之后某处，形状一样但含义完全不同 ——
这就是「参照系不明」换个地方复发。代价是 ①③ 看不到 2014–2018（含 2015 年 4.70% 那个历史峰值）。

⚠ **纵轴范围必须重算，不能沿用基准期的分位切点。** 这里踩了两个坑：
- 只按窗口内 2%~98% 分位取 → ① 在 2019 后的最高是 **2.901**，而 p98 只有 2.74，**曲线顶出画布**；
- 只把「档位边界」包进来也不够 → ① 的「很高」边界 2.761 若落在轴外，**最高那一档的色带画不出来**，读者只看到三档。
- 最终：`轴 = min(窗口真实最低, 最低边界, 0若跨零) ~ max(窗口真实最高, 最高边界)`，两端各留 4% 余量。

⚠ 图中的**色带顺序**踩过一次坑：第一版把「从高到低画」配上「从低到高排的颜色」，
结果一条淡蓝盖住大半张图，四档全看不出来。**画完必须看截图，不能只看代码对不对。**

⚠ 小图的色带透明度要比大图高得多（.08~.19 vs .032~.075）：170px 高的小图上，
同一组淡色根本分不出来，实测截图里四段看着像一整块。**这不是审美问题，是可读性问题。**

⚠ `pointRadius` 只接受数字或 scriptable 函数，**传数组会静默忽略**（不报错也不生效）。

⚠ `yearAxis(labels, {ticks:{...}})` 会把整个 `ticks` 对象换掉，`callback` / `afterBuildTicks`
一起没了，**横轴直接显示成 `2019-01-02` 这种完整日期**。要改刻度只能覆盖 `afterBuildTicks`。

#### 11.4.2 三张小图之外，为什么还要单独一张全历史（2026-11-12 追加）

用户第三句原话：**「增加杠杆水位的曲线图」**。

这一句是对 11.4.1 那个设计的直接补正：**三张小图为了横向可比，把起点绑在 2019-01-02，
于是 ① 看不到 2015-07-03 的 4.697%。**而那个峰恰恰是回答「现在 2.49% 算不算高」的唯一锚点。

没有它，读者只能在 2019 年以来的窄区间里比 —— 而那个区间的最高点只有 2.90%（2026-07-13），
**看起来 2.49% 已经快到天花板了**；放回 12 年尺度才看得出：**它离历史峰顶还差 46.9%。**

这两句话的情绪是完全相反的。同一根曲线，换个窗口，结论反了。

##### 单独一张，不和那两张并排

| | 全历史大图 | 三张小图 |
|---|---|---|
| 跨度 | 2014-01-02 → 2026-11-11（**3125 天**） | 2019-01-02 起（**1905 天**） |
| 时间尺度 | 宽 | 窄 |
| 用途 | 回答「历史上到过哪」 | 回答「现在在三档里的哪一档」 |
| 布局 | **独占一行**，上方有 `border-top` 分隔线 | 三列并排 |

⚠ **不能并排。** 同样像素宽度代表的时间跨度不同（12 年 vs 7 年），并排就会诱导读者
横着比形状 —— 左图爬一年等于右图爬七个月，形状一样含义不同。
**位置本身就在说「别横着比」**，这比写一段说明更有效。

顺带把「谷」也标出来：**2014-01-02 的 1.726%**（两融刚规范化那阵）。
峰与谷都在图上，读者才知道 2.49% 在这个区间里到底偏哪边。

##### `gap_from_peak` 怎么读

后端给的是 `(当前 ÷ 峰顶 − 1) × 100 = −46.9%`，页面上写「距 2015 峰顶 −46.9%」。

**这个数比「79.6% 分位」好用**，理由是它不需要读者懂分位是什么：

> 最疯的时候每 100 元流通股借了 4.70 元，现在借了 2.49 元 —— **还不到那时的一半**。

而「79.6% 分位」要读者先在脑子里建立「历史分布长什么样」才能读，对第一次看的人等于没说。
**两个都给：分位给懂的人，距峰顶给不懂的人。**

##### 这轮踩的两个新坑

**① `suggestedMin/suggestedMax` 不是硬边界，轴会被外扩。**

改成硬边界之前，③ 的数据只到 **+19.5%**，而 Chart.js 把轴拉到了 **+40%** ——
上半张图整片空白，曲线被压在下半截，四档色带最上面那一档也几乎看不见。
① 的轴同样被从 4.79 拉到 5.0，峰顶离顶部留出一段白。

原因：`suggested*` 只是「建议起点」，Chart.js 仍会向外找整齐刻度。
后端算的 `axis` 本身已经是「真实极值 ∪ 档位边界 + 余量」，直接 `min/max` 照用就够。

**② 换成硬边界之后，峰谷标注掉出画布。**

原来写「峰标上方、谷标下方」。硬边界后谷点离轴底只剩 5px，写下面就**被裁掉一半**；
想给峰留空间就得把轴重新撑到 5.0 —— 那正是刚修掉的问题。

改法：**两个标注都放点的右侧、同一高度**（右侧永远有空白，且不需要任何纵向留白），
再加一圈白色描边防止压住曲线；放不下就翻到左边。

| | 改法前 | 改法后 |
|---|---|---|
| 位置 | 峰上 / 谷下 | **都在点的右侧** |
| 边界 | 靠轴外留白保住 | 坐标钳到 `[a.top+7, a.bottom-7]` 内 |
| 可读性 | 谷标被裁 | 白描边 `strokeText` 打底 |

⚠ **这一类错的共同点：`min/max` 一改，所有「相对点位」的绘制全要重算。**
这次只改了轴，没同步改标注的定位规则，才让谷标掉出去。

##### 代码结构：三个零件抽成工厂

大图和三张小图的色带 / 零线 / 当前值虚线逻辑完全一样，只有尺寸不同。
第一版在四个地方各写一遍 —— 改色带时改了两处漏了一处，漏的那张看起来「淡一点」，很难发现。

现在抽成三个工厂（`demo.html` 内）：

| 工厂 | 参数 | 说明 |
|---|---|---|
| `makeBands(id, cuts, fills, lineAlpha)` | 分界 / 4 个颜色 / 边线透明度 | 色带 + 边界细虚线 |
| `makeCur(id, val, col, txt, opt)` | 当前值 / 颜色 / 标签文字 / 字号 | 虚线 + 右端标签 |
| `makeZero(id, on)` | 是否启用 | 零线，只有 ③ 用 |

透明度做成参数，因为**小图必须比大图浓得多**（见 11.4.1 那条）。
同时删掉了 `BANDS[k].cols` / `.fills` 两份从没被读过的重复数据 —— 留着只会让人以为改那里就有效。

### ⚠ 对齐陷阱（这次差点写错）

三个数据的披露节奏不同：

| 数据 | 最新日期 | 为什么 |
|---|---|---|
| ETF 份额 | 2026-11-10 | T+1 披露 |
| 两市成交额 | 2026-11-11 | T 日当晚可得 |
| 两融余额 | 2026-11-11 | T+1 晚间公布 |

**不能强行对齐到份额的 `days` 序列** —— 会把 11-11 的成交额丢掉，量能指标永久滞后一天。
所以量能和两融各用自己的自然交易日序列，只在面板显示时按日期取值。
面板上分别标注三个日期，不合并成一个「今天」。

### ⚠ 盘中陷阱

接口在交易时段会返回**当日未收盘**的数据。实测 2026-11-12 10:21 抓取，
当日成交额只有 8,486 亿（半日量），而 11-11 全天是 16,762 亿。
若不剔除，页面会把「半天」当「全天」，量能萎缩 50% 的假信号就出来了。

#### ⚠⚠ 但当时的处理方式是错的（2026-11-12 晚更正）

原文这里写的是「`fetch_index.py` 只接受日期 `< 今天` 的记录」。
**这条规则本身把一个真问题修成了另一个假问题**：

| | 上午的写法 | 问题 |
|---|---|---|
| 判据 | `p[0] >= today → 丢弃` | 「今天」≠「今天没定稿」 |
| 结果 | CI 在北京 **18:38** 跑（收盘后 3 小时 38 分），当日数据早已定稿，仍然被扔掉 | 末日期永远停在 T-1 |
| 后果 | 页面天天显示「落后 1 天」 | **永远修不好，因为每天都被扔一次** |

真正的判据不是「是不是今天」，而是**「今天这一根定稿了没有」**：

```python
# scripts/_td.py
CLOSE_HHMM = (15, 10)          # 15:00 收盘 + 10 分钟定稿缓冲

def accept_day(d):
    t = bj_today_str()
    if d < t: return True       # 昨天以前一定定稿
    if d > t: return False      # 未来日期 = 脏数据
    return today_allowable()[0] # 今天要看时钟：过 15:10 才要
```

三个抓取脚本（`fetch_index.py` / `fetch_price_bfq.py` / `fetch_history.py`）
原来**各自**写了一遍 `>= today`，现在统一走 `_td.accept_day()`。

⚠ **这条错误的教训不是「忘了收盘时间」，而是「一个天天亮的提示等于没装」。**
我上午刚在 `_fh.py` 里写下「周末必红会被当成噪音关掉」，
下午就在另一个文件里造了一条**每天必然为琥珀**的提示 —— 同一个死法，换个地方复发。

## 十三、市场共识层（2026-11-13 新增）

前十二节全部是**事实层**：份额、价格、净流入、两融。有权威出处，可回溯，错了拿原始数据一对就清楚。

第十三节是另一样东西：**别人在怎么说**。它不产生交易信号，只产生「共识读数」。

### 13.1 为什么单独一栏而不是混进事实层

| | 事实层 | 共识层 |
|---|---|---|
| 内容 | 交易所份额、行情价格 | 媒体标题、股吧帖子、热度榜 |
| 出错方式 | 抓错了（可核对） | **抓对了但归纳错了**（无法核对） |
| 回答 | 发生了什么 | 大家在说什么 |

所以页面上它单开一栏（`pane-consensus`），并且每一块都写着「这是什么 / 它不能拿来干什么」。

### 13.2 四个数据源（2026-11-13 全部实测）

|---|---|---|
| 蛋卷 `index_eva/dj` | 63 个指数 PE/PB 历史分位 + 股息率 | ✅ 匹配上 17 个 |

| 东财股吧 | 散户原话 | ⚠ 可抓但**会限流**，需退避重试 |
| 腾讯 `qt.gtimg.cn` | 创业板指当日涨跌（事实锚） | ✅ 1 次成功 |

**确认关闭的路（不要重试）**：抖音搜索（`status_code 2483` 需登录）、抖音视频详情（403）、
抖音用户主页（0B）、**抖音热榜（147 条采样财经命中 0 条）**、小红书写 `search_result`、

### 13.3 「抖音博主判断」这件事的结论

OO 的原话是要「抖音上财经博主的判断，比如陈小群」。实测结论：

- **拿不到**他本人的每日观点（搜索需登录、详情 403、热榜无财经）
- **能拿到**关于他的新闻 —— 而且当天拿到的是「塌房」「深陷收割争议」

所以页面上没有「陈小群今天说了什么」，只有「媒体今天在报什么」。
这一句写在页面口径里，不能省 —— 省了就等于暗示抓到了。

### 13.4 算法迭代：三次才找对路子

| 版本 | 做法 | 结果 | 错在哪 |
|---|---|---|---|
| v1 | n-gram 滑窗 + 双向包含去重 | Top1 是「创业板指」 | 抽出了**主语**，不是主张 |
| v2 | 加 `SUBJECT`/`EVENT` 词表过滤 | 只剩 1 条，还有碎片「业板指跌」 | **打补丁治不了切法本身产生的碎片** |
| v3 | **按主题聚合**（`TOPIC_LEX` 19 主题） | A股 6 条、黄金 2 条，全部可读 | 对 |

核心认识：**中文财经标题对同一件事有 5 种写法**（「算力硬件股集体下挫」「算力硬件概念集体下挫」
「算力硬件股领跌」「算力硬件方向领跌」「算力概念下挫」）。精确短语匹配会把它们拆成
5 个各 1 家的孤岛，全被 `min_src=3` 滤掉。**必须先归到主题，再数主题。**

### 13.5 方向判定的四条纪律

1. **取离主题最近的方向词，不是整句多数票**
   「银行板块逆势拉升 创业板指跌3.32% 算力硬件下挫」——整句「跌」相关 3 个、「拉升」1 个，
   多数票会把银行判成跌。

2. **head 只取主题词本身，不取前面的字**
   「A股三大指数收跌 影视板块逆市大涨」——影视板块前面 2 字正好是「收跌」。
   **宁可漏掉罕见的倒装，也不能借错谓语**：漏了只是少一条，借错是给出反向结论。

3. **词表必须对称**
   `DIR_UP` 26 个 / `DIR_DOWN` 26 个（差 ≤ 3 有测试守着）。
   只收「跌」不收「涨」，每天看起来都在崩 —— 那不是市场，是词表。
   2026-11-13 补了「失守/跌破/击穿/探底」，因为「现货黄金失守3870美元」被判成 flat。

4. **一个位置只能归一个主题**
   「A股市场震荡调整 AI短剧概念再度走强」同时命中 `AI短剧`（AI应用）和 `AI`（人工智能）。
   不消解重叠，一条标题就给两个主题各投一票涨 —— 而「偏涨主题 5 个」正是第一票的依据。

### 13.6 四个被实测揪出来的真缺陷（都在页面上错过数）

| # | 缺陷 | 现象 | 修法 |
|---|---|---|---|
| 1 | **分母不一致** | 页面写「黄金 在跌 21 家」，实际是 21 家提到、16 家说跌、4 家没方向 | 分列「提到/说涨/说跌/没方向」，强制 说涨+说跌+没方向 == 提到 |
| 2 | **分项和 > 总量** | 一家媒体既发「金价跌」又发「法兴唱多」，两边各算一次 → 17+10=27 > 21 | 加 per-src 计数层，每家按篇数多的那边归一次 |
| 3 | **主题重叠双计** | 一条标题命中 2 个语义包含主题 | 长词优先 + 贪心消除位置重叠 |
| 4 | **视角缺失** | 板块词表判「偏强」，而当天创业板指跌 3.32% | **补第四票：当天大盘涨跌**（从行情接口直接读） |

第 4 条最要紧。56 篇 A股新闻里 **33 篇（59%）** 是「创业板指跌3%」这类指数级播报 ——
词表按板块组织，指数名一个都没收。所以「媒体主题方向」这一票只覆盖 **41%** 的报道。
一个说「偏强」而当天指数跌 3% 的判断，逻辑再自洽也是误导。

修法不是去扩词表（指数播报永远比板块多），而是**补一票事实锚**，
并把覆盖率 41% 直接印在页面上 —— 覆盖率低的结论不是错，是**不能单独当结论**。

### 13.7 判断：四票制

| 票 | 来源 | 说明 |
|---|---|---|
| 媒体主题方向 | 东财搜索 | 按**家数**加权，不是数主题个数 |
| 股吧散户方向 | 东财股吧 | 分母写明「有明确态度的几条」 |
| 估值分位中枢 | 蛋卷 | 17 个指数平均 PE 分位 |
| **当天大盘涨跌** | 腾讯行情 | 唯一的事实锚，不经词表 |

判定：全正 → 一致偏强｜全负 → 一致偏弱｜≥2 且多于对方 → 偏强/偏弱｜其余 → 分化。

**必须同时给「支撑证据」和「反面证据」**，只给支持自己结论的证据就是话术。
反面证据里会自动写出背离，例如：

> 媒体在说板块「偏涨」（15 家次 vs 3 家次），但当天创业板指跌 3.32% ——
> 板块热度和大盘方向对着走，说明涨的是少数板块，不是市场整体在涨

**缺票必须写进结论。** 2026-11-13 股吧被限流返回 0 条，那一票直接消失，
判断从四票变三票但措辞没变 —— 读者会以为「散户没表态」，实际是「没抓到」。
现在结论后面会跟一句「（注意：股吧今天没抓到帖子，散户情绪这一票缺席）」。

### 13.8 热度分位的诚实性

`MIN_SAMPLE_DAYS = 20`。样本 < 20 天时 `percentile_of` 返回 `None`，页面显示「样本 N/20 天」。

**不要用「当前值 / 历史最大值」冒充分位** —— 那是最大值占比，不是分位。
分母用「严格小于等于的天数」。样本不足时说「样本不足」，不编一个数。

2026-11-13 首跑，历史 0 天，全部 8 项分位都是 `None`，页面如实显示「样本 0/20 天」。
这不是没做好，这是唯一诚实的做法。

### 13.9 顺带发现的一个对框架有直接影响的事实

2026-11-13 估值分位读数：

| 贵的一端 | 分位 | 便宜的一端 | 分位 |
|---|---|---|---|
| 标普红利 | 99.7% | 证券公司 | 0.7% |
| 上证红利 | 98.4% | 创业板 | 6.0% |
| 中证银行 | 98.4% | 恒生科技 | 7.2% |
| 300红利LV | 94.7% | 中证医疗 | 10.6% |
| 中证红利 | 87.4% | 新能源车 | 7.7% |

**红利已经不便宜了。** 这对「40% 现金流盘靠股息托底」是必须先看见的事实：
托底的那一半资产，现在处在自己历史上最贵的区间之一。

⚠ 但分位只回答「贵不贵」，**不回答「会涨还是会跌」**。贵可以更贵。
它的真正用处是：同样一笔新增的钱，放在低分位的地方，长期赔率更好。
